第 10 章：性能调优与精度评估

章节目标：从「能跑」到「跑得快」——掌握 NPU 核心数 / batch / 量化配置 / CPU+NPU 混合 / 投机解码几大手段，能在给定延迟目标下调出达标配置，并说清每一步为什么有效。

课堂讲义（板书）

讲解0. 这节课到底学什么

性能调优不是「多试几次碰运气」，而是先建指标、再测基线、然后一次只动一个变量。你作为架构师要能说：这个配置为什么快、瓶颈在哪、还有多少空间。

你要能四件事：① 说清看哪些性能指标；② 会建基线和算 Amdahl 上限；③ 会跑配置矩阵找最优；④ 给一个延迟目标，能反推出该动哪些旋钮。

讲解1. 板书①：性能指标体系（先会量，才会调）

「快」是个模糊词。端侧对话至少拆成两组指标：首响（prefill）和吐字（decode），二者瓶颈完全不同。

五个必测指标 ① TTFT（首 token 时延） 用户按下回车到第一个字出现 ≈ prompt_tokens ÷ prefill 吞吐(tok/s) 受算力影响大（prefill 是算力瓶颈） ② decode tok/s（吐字速度） 生成阶段每秒出多少 token 受带宽影响大（每 token 读一遍全部权重） ③ 内存占用（RSS / 模型常驻） free -m / nvidia-smi 类比 → 端侧用 free、/proc/self/status ④ NPU 利用率 cat /sys/kernel/debug/rknpu/load （看到百分比） ⑤ 带宽利用率 = decode_tok/s × 模型真实GB ÷ 有效带宽上限（NPU 独占 12~16 GB/s） 判断"是不是带宽瓶颈"的核心尺子 一句话：新用户感受 TTFT，长时间对话感受 decode tok/s。

讲解2. 板书②：基线 + Amdahl（优化前先算天花板）

没基线就没优化。先测「什么都不改」的原始数字，再算理论加速上限，避免白忙。

基线表（先填原始配置） 配置 TTFT decode 内存 NPU 带宽利用率 baseline 1200ms 6.0 t/s 2.1GB 70% 75.0% ... Amdahl 定律：先看瓶颈占总时间多少 加速比 = 1 / ( (1−p) + p/S ) p = 可优化部分占比， S = 该部分加速倍数 例：耗时 80% 在量化可加速的 NPU 算子，若把它加速 4 倍 加速比 = 1 / (0.2 + 0.8/4) = 1 / 0.4 = 2.5× → 就算把 NPU 部分优化到极限，整体最多 2.5 倍，别指望 5 倍 结论：先优化占比最大的那部分，收益最大。
面试加分点：「我会先测 baseline 和 Amdahl 上限，确认瓶颈占比，再决定投入——不做没有上界的优化。」

讲解3. 板书③：三旋钮实测矩阵（核心实操）

三大旋钮：量化配置、NPU 核心数、batch size。做法：固定其他，一次动一个，填进矩阵。

旋钮一：量化配置 w4a16 最省内存、最快，精度略降 ← 端侧默认起点 w8a16 精度更好，慢约 15~30% w8a8 最稳，LLM 上未必最快 旋钮二：NPU 核心数 num_npu_core 3576 单核，固定 1（没得调）； 3588 三核，实测 1→2 核近线性、2→3 核收益递减（带宽抢用）。 旋钮三：batch size（并发数） 单路 bandwidth-bound，多路可"摊薄"权重读取： batch=1 → 6.0 t/s，带宽利用率 75.0% batch=4 → 7.6 t/s（合计），利用率 95% batch=8 → 7.9 t/s（合计），利用率 98%，但单路 TTFT 变差 batching 提吞吐、不降延迟——适合多用户服务端场景。

规律：batch 越大越接近带宽上限，但收益递减；到 8 路只多 0.3 t/s，成本（内存×8、TTFT 变差）不划算——这就是「甜点」在哪的判断。

讲解4. 板书④：CPU + NPU 混合调度

NPU 不是万能的：有些算子 NPU 不支持或支持差（如某些动态 shape、特殊激活、非标准 attention）。这些会回退（fallback）到 CPU，一旦掉 CPU 就会拖慢整体。

混合调度三原则 ① 能塞 NPU 的就塞 NPU —— 主体矩阵乘全部 NPU 化 ② 掉 CPU 的算子要盯住 —— 看 build 日志的 "not supported" ③ 减少 NPU↔CPU 数据搬运 —— 搬运 = 额外带宽 + 时延 判断是否掉 CPU： 跑推理时 top 看主进程 CPU% —— 若 CPU 长期 100%+ 且 NPU 利用率低 → 多半有算子掉 CPU 典型分工： Prefill 大矩阵乘 → NPU（算力密集） sampling/采样 → CPU（轻量、控制逻辑） tokenizer → CPU 目标：让 NPU 干重活、CPU 干调度，别让 CPU 抢带宽。

讲解5. 板书⑤：投机解码（speculative decoding）

思路：用小模型（draft）先猜几个 token，再用大模型（target）一次验证。猜对了就白赚——因为大模型一次前向能确认多个 token，分摊了权重读取，正好打带宽瓶颈。

参数：γ = 每轮猜几个；α = 猜中率(acceptance rate)；r = 小/大模型耗时比 手算（α=0.8, γ=4, r=0.1） 每轮平均猜中数 = α(1−α^γ)/(1−α) = 0.8 × (1 − 0.8⁴) / 0.2 = 0.8 × (1 − 0.4096) / 0.2 = 0.8 × 0.5904 / 0.2 = 2.3616 每轮总产出 = 猜中 + 1（大模型兜底）= 1 + 2.3616 = 3.36 token 每轮耗时 = γ·r + 1 = 4×0.1 + 1 = 1.4（相对大模型单次前向） 加速比 = 3.36 / 1.4 = ≈ 2.4× 结论：猜中率 α 越高、小模型越便宜(r 越小)，加速比越大。 α 太低或小模型太重 → 反而变慢，要果断关掉。 llama.cpp 支持：--model big.gguf --model-draft small.gguf （-md 指定草稿模型；--draft-max 控制 γ）
为什么端侧特别值：decode 是带宽瓶颈，投机解码让一次权重读取服务多个 token，本质是提升带宽利用率——和第 9 章那把尺子对上了。

讲解6. 板书⑥：找最优组合（配置矩阵 + 帕累托）

实验矩阵（示例，一次动一个变量） # quant core batch TTFT decode 内存 带宽利用 1 w4a16 1 1 1200ms 6.0 t/s 2.1GB 75.0% 2 w8a16 1 1 1300ms 5.0 t/s 2.4GB 62.5% 3 w4a16 1 4 1500ms 7.6 t/s 2.9GB 95.0% 4 w4a16 1 8 1700ms 7.9 t/s 3.6GB 98.8% 5 w4a16+投机 1 1 900ms 7.2 t/s 2.5GB 90.0% 选型原则：按目标选，不是越大越好 要低延迟单路对话 → 选 5（投机解码）：TTFT 低、tok/s 高 要多用户高吞吐 → 选 3（batch=4）：最平衡 要极致精度 → 选 2（w8a16）：慢但准 在"满足延迟目标"的候选里，挑内存最小的那个

讲解7. 板书⑦：给延迟目标反推配置

任务：3B int4，目标 decode ≥ 6 tok/s（NPU 独占），内存 ≤ 4GB ① 理论天花板（NPU 独占）：16 ÷ 2.0 = 8.0 t/s → 目标 6 可达，需高利用率 ② 目标利用率：6 × 2.0 ÷ 16 = 75% ③ 单路(w4a16) 6.0 t/s = 75%，刚好达标；产品场景会掉到 3.5~5.5 ④ 手段： - batch=4 → 7.6 t/s（95%）✅ 内存 2.9GB（≤4GB）；单路 TTFT 变差 - 投机解码 → 7.2 t/s（90%），单路低延迟优先 - batching + 投机 组合 → 冲 95%+ ⑤ 结论：先保单路达 6 tok/s，再用 batch 或投机解码冲利用率 被问"给个延迟目标怎么调"→ 标准答： 「先算理论天花板确认目标可达 → 再算需要的带宽利用率 → 若单路不够，就上 batch（提吞吐）或投机解码（摊薄权重读取）→ 在满足目标的方案里挑内存最小、最稳的那个。」

讲解8. 板书⑧：精度评估闭环（量化后第一件事）

完成转换 / 量化后，第一件事不是压性能，而是评精度。速度再快，答案错了就是废品。评估要先定指标、再定流程、最后定上线门槛——一步都不能省。

按任务选指标（选错指标 = 白评） LLM / 语言模型 → PPL（困惑度，越低越好） + 抽样人肉问答（有没有事实错误） 检测 / 分割 → mAP（IoU 阈值下的平均精度） + mIoU（分割） 分类 → Top-1 / Top-5 准确率 回归 / 关键点 / 深度 → RMSE / MAE（越小越好） 一句话：语言看 PPL，检测看 mAP，回归看 RMSE/MAE。 别用「感觉变笨了」判断——那是感觉，不是指标。
评估流程（固定验证集是关键） ① 固定验证集：量化前就切好一份不参与校准的测试集， 之后每次量化都用同一份——可比才有意义。 ② 跑原始模型：先测 FP / 原始精度 baseline。 ③ 跑量化模型：同验证集、同指标、同脚本。 ④ 前后对比：算 Δ（绝对差 + 相对涨幅）。 ⑤ 判定：对照门槛决定「上线 / 调优 / 回退」。 门槛参考 PPL 涨幅 <5% / mAP 掉点 <1pt / RMSE 涨幅 <5% → 可上线 超门槛 → 先补校准集（板书⑩），不行再上 QAT（板书⑩）
纪律：校准集和验证集必须分开。拿校准集去评精度 = 自己给自己出题还提前看答案，涨幅必然好看，线上必崩。

讲解9. 板书⑨：量化误差分析（找出塌掉的那一层）

精度不达标时，别急着换方案——先定位误差出自哪一层。量化误差是逐层累积的，找到「罪魁层」，往往只改一个配置就能救。

两种定位粒度 逐层（per-layer） 逐层把量化张量与原始张量比对： · 相对误差 = ‖W_q − W‖ / ‖W‖ · 余弦相似度 = cos(W_q, W) 找误差突然变大的那一层 / 那一段（常是 attention 输出、 FFN 第二个矩阵、LayerNorm 附近）。 逐通道（per-channel） 对每层再按输出通道拆，找「离群通道」： · 某通道 scale 被 outlier 撑大 → 同层其他通道全被压平 · 这正是第 2 章 outlier 陷阱的「逐层放大版」 判读 · 单层相对误差 > 10% → 该层敏感，优先保精度； · 误差集中在个别通道 → 该层需要 group-wise 或提高位宽。
误差定位后的三板斧 ① 该层单独保精度：敏感层抬到 w8a16 / 保持 fp16； ② 缩小 group_size：让 outlier 关进更小的组（回顾第 2 章）； ③ 换 quantized_algorithm：normal → mmse / kl_divergence， 让标定更贴合分布。

讲解10. 板书⑩：校准集工程 + PTQ/QAT 验证

精度问题的根治手段只有两个：校准集做对，或 PTQ 不够就上 QAT。先榨干校准集，再决定要不要动 QAT——QAT 成本高得多。

校准集工程（覆盖真实分布） · 分布对齐：用线上真实输入，不用随机数（第 9 章的校准集三条军规）。 · 分层覆盖：长度（短/中/长）、任务（问答/翻译/代码）、 边界样本（超长、含数字、含专有名词）都要有。 · 规模：LLM 100~500 条；太少统计不稳，太多收益递减。 · 一致性：校准集与上线输入同源、同预处理管线， 否则「校准的世界」和「运行的世界」是两回事。 · 可复现：固定随机种子与采样脚本，存 calib/prompts.txt。
PTQ vs QAT PTQ（训练后量化）——首选 不训练，只校准；快、成本低。 覆盖 80% 场景；w4a16 / w8a8 通常够用。 QAT（量化感知训练）——PTQ 不行才上 训练时模拟量化误差，让模型「学会」在量化下工作； 精度最接近原始，但要重训 + 数据 + 算力。 适合：PTQ 后仍超门槛、且该模型值得投入。
验证闭环（PTQ / QAT 都要走） 校准集 → 量化 → 固定验证集评测 → 对比 baseline → 达标 → 上线 不达标 → 换校准集重来 → 仍不达标 → 上 QAT → 再评测 每一版量化都留一份评测记录，可追溯到「哪一版达标」。
顺序别乱：先 PTQ + 好校准集（性价比最高），实在过不了门槛再上 QAT。一上来就 QAT = 用最贵的办法解决最便宜的问题。

上午任务 4h

1

性能指标采集脚本

目标
写一个脚本，一次跑出 TTFT / decode / 内存 / NPU / 带宽利用率五项。
要掌握
五项指标的取法（free、/sys/kernel/debug/rknpu/load、计时首 token）。
实操步骤
写 bench.sh：跑一次推理，用 date +%s.%N 计 TTFT，统计 decode tok/s，抓内存与 NPU load，输出 baseline.txt。
检验标准
脚本一条命令出五项数字，重跑误差在合理范围。
2

基线 + Amdahl 上限计算

目标
建基线表，并用 Amdahl 算出理论加速上限。
要掌握
Amdahl 公式；如何估「可优化部分占比 p」。
实操步骤
把 baseline 数字填表；假设 NPU 部分占 80%、能加速 4 倍，手算上限写入 amdahl.md。
检验标准
能说出「整体最多几倍」并解释为什么不是叠加。
3

CPU+NPU 分工排查

目标
找出哪些算子在 CPU 上跑（fallback）。
要掌握
怎么从 build 日志 / top 判断掉 CPU；为什么搬运要避免。
实操步骤
跑推理，top 记录主进程 CPU%；翻 build 日志找 "not supported"；写 cpu_npu_split.md 列出候选 fallback 算子。
检验标准
能指出至少 1 个疑似掉 CPU 的算子，并说清它对带宽/时延的影响。

下午任务 4h

1

配置矩阵实测（核心实操）

目标
跑通板书③⑥的矩阵：量化 × batch（× 投机），填满性能表。
要掌握
「一次只动一个变量」；batch 对吞吐/带宽利用率的影响。
实操步骤
至少跑 5 组配置，用 bench.sh 采集，写入 perf_matrix.md（含 TTFT/decode/内存/带宽利用率列）。
检验标准
表里能看出「batch 越大利用率越高、收益递减」的趋势。
2

投机解码验证

目标
用 llama.cpp 草稿模型跑一次投机解码，测实际加速比。
要掌握
γ/α/r 三参数；加速比手算公式；α 低时为何要关。
实操步骤
用 llama-cli --model big --model-draft small 对比开关前后 tok/s，记录 α 与实测加速比，写入 spec_decode.md。
检验标准
能对比手算与实测加速比，并给出「是否值得开」的结论。
3

《性能调优报告（含最优配置）》（本章核心产出）

目标
综合矩阵与实验，给出最优配置与理由——一页纸。
要掌握
把指标 + Amdahl + 矩阵 + 投机解码串成一个决策。
实操步骤
写 perf_tuning_report.md（一页）：①基线 ②Amdahl 上界 ③配置矩阵 ④最优配置（含延迟/内存/带宽利用率）⑤从目标反推的调优路径。
检验标准
给定一个延迟目标，拿报告能立刻选出配置——架构决策标准。
4

精度评估脚本模板（新增）

目标
写一个可复用的评估脚本模板：LLM 算 PPL，或检测算 mAP。
要掌握
固定验证集的做法；PPL / mAP / RMSE 的取法；量化前后对比与门槛判定。
实操步骤
① 切一份不参与校准的验证集 eval/；② 写 eval_ppl.py（读验证集逐 token 累加 logp，PPL=exp(-mean(logp))）或 eval_map.py（跑检测框、按 IoU 计算 AP 后求均值）；③ 同一脚本跑原始模型与量化模型，输出 eval_report.md：baseline / 量化 / Δ / 是否达标。
检验标准
改配置不用改脚本就能重测；报告里能指着数字说清「涨/跌多少、为什么、是否上线」。

检验标准（自测）

  • 给一个延迟目标，能反推出该动 batch 还是投机解码。
  • 能按任务选对精度指标（LLM 用 PPL、检测用 mAP、回归用 RMSE/MAE），并用固定验证集做前后对比。
  • 能定位量化误差最大的层，并说出「PTQ 不够就上 QAT」的判定顺序。

面试话术

可直接背

「我做端侧性能调优先建指标：TTFT、decode tok/s、内存、NPU 利用率、带宽利用率。先测 baseline 再用 Amdahl 算理论上界，确认瓶颈占比。优化手段上：量化配置在 w4a16/w8a16 间权衡精度与速度；batch size 能提升吞吐和带宽利用率，多用户服务端优先；CPU+NPU 混合调度让 NPU 干矩阵乘、CPU 干采样和 tokenizer，尽量避免算子掉 CPU 造成搬运；单路低延迟场景用投机解码，用小模型猜、大模型验证，让一次权重读取服务多个 token，实测能到 2 倍左右加速。最后按目标在候选里挑内存最小、最稳的配置。」

能力标签：能建指标、定基线、算上界、跑矩阵，给延迟目标调出达标配置——性能调优能力。

RK3576 特别提示

  • 3576 是单核 NPU，num_npu_core 固定 1，调核心数没意义；这一点要说清，别照搬 3588 的经验。
  • 带宽三档（峰值 19 / NPU 独占 12~16 / 产品 7~11 GB/s），batch 与投机解码是提升带宽利用率的正路；超过 ~95% 利用率后收益递减。
  • NPU 利用率看 /sys/kernel/debug/rknpu/load；若 CPU 长期 ≥100% 而 NPU 低，说明有算子掉 CPU（fallback），要回第 9 章查 build 日志。
  • 内存有限，batch 翻倍内存也翻倍——3B int4 batch=8 约 3.6GB，别再叠加其它服务。
