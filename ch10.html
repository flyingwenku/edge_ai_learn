课堂讲义（板书）

讲解0. 这节课到底学什么

CV（计算机视觉）检测是端侧最成熟的一类落地任务：模型小、算子规整、工具链支持好。别的领域还在摸索，CV 已经有了标准答案。所以这一章的深度不是「从零训练一个检测网络」，而是「全链路能跑通、每步的坑能讲清」：你会走完 6 步，会用 mAP 判断量化做得好不好，并理解为什么回归头比分类头更怕量化。

深度定位：量化算法、粒度这些「重活」厂商工具链（RKNN Toolkit）已经封装好了——int8 per-channel 是默认配置，你不需要手写。你要做的只有两件事：① 校准集是否覆盖真实场景；② 量化后 mAP 是否达标。

讲解1. 板书①：CV 任务与选型

先分清 CV 的三大任务，各自的输出不同、选型也不同。

CV 三大任务 检测 detection ：找出"是什么、在哪" → 输出 bbox + 类别 端侧代表：YOLOv8n / PP-YOLOE-s 分类 classification：判断"整张图是什么" → 输出 1 个类别 端侧代表：MobileNetV3 / EfficientNet-Lite 分割 segmentation ：分到"每个像素属于谁" → 输出掩码 mask 端侧代表：PP-LiteSeg / 轻量 DeepLab 端侧选型三原则：参数少 + 算子规整 + 有现成预训练 检测：YOLOv8n（约 3.2M 参数，fp32 约 6MB）最通用 PP-YOLOE-s（国产 Paddle 系，工具链友好） 分类：MobileNetV3（约 2.5M） 分割：PP-LiteSeg（端侧偏重，优先做检测/分类） 为什么 CV 端侧成熟（记这 4 条）： ① 模型小：检测网络才几 MB，fp32 都塞得进内存 ② 算子规整：卷积 / BN / 激活为主，NPU 支持成熟 ③ 预训练多：COCO 上现成权重，多数场景只做"转换+量化" ④ 工具链好：ONNX → RKNN 顺畅，量化配置已封装

讲解2. 板书②：CV 代表网络（结构要点，不推公式）

不背公式，只记每个部件在物理上干什么。

CNN 三个核心操作的物理含义 卷积 conv：滑动小窗口只看局部（局部感受野）， 同一组权重到处复用（权值共享） → 从像素里抽出边缘 / 纹理 / 形状 池化 pool：下采样、放大感受野，让后面的层"看得更广" 激活 + BN：引入非线性、把数值拉回稳定范围（利于量化） YOLO 结构三段（检测通用骨架） Backbone 主干：CSPDarknet，逐层从像素 → 特征图，抽"语义" Neck 颈部 ：PAN-FPN，把深层的"语义"和浅层的"位置"融合 Head 头部 ：解耦检测头，每个网格预测 bbox + 类别 + 置信度 一句话：backbone 认"是什么"，neck 合"位置+语义"， head 吐"框和类"。 端侧只关心：这三段算子规整不规整、能不能落到 NPU。

讲解3. 板书③：数据与标注（COCO / YOLO 格式）

标注格式就两种主流，看懂就能转。

两种主流标注格式 COCO（json 单文件管全部图） images[] ：file_name / width / height annotations[] ：bbox = [x, y, w, h] 左上角 + 宽高，像素单位 category_id / image_id categories[] ：类别表（id ↔ name） YOLO（每张图一个 txt，每行一个框） class cx cy w h 全部归一化到 0~1（中心点 + 宽高） 端侧常见做法：能不重训就不重训 下载官方 / 开源预训练权重（.pt / .onnx）→ 直接转 RKNN 用。 只有类别对不上（如自有工业缺陷）才微调，且微调在 PC 上做。 标注质量决定精度上限：漏标 = 训练时被当负样本， mAP 会被拉低（或虚高）。
格式换算（COCO 像素 ⇄ YOLO 归一化） COCO bbox = [x, y, w, h]（左上角） → cx = (x + w/2) / W_img cy = (y + h/2) / H_img w' = w / W_img h' = h / H_img 例：图 640×480，bbox=[100, 60, 200, 120] cx=(100+100)/640=0.3125 cy=(60+60)/480=0.25 w'=200/640=0.3125 h'=120/480=0.25 转标注、写评估脚本都要反复用这个换算。

讲解4. 板书④：导出 ONNX（转 RKNN 报错的重灾区）

PyTorch → ONNX：torch.onnx.export(...) torch.onnx.export(model, dummy_input, "yolov8n.onnx", opset_version=12, input_names=["images"], output_names=["output"]) 三个常见坑（转 RKNN 报错大多出在这） ① opset 版本：RKNN 支持的 opset 有上限（常见 11/12）， 太新可能带来不支持的算子 ② 动态 shape：端侧固定输入更稳；导出时固定 batch=1、H=W=640，别留动态维 ③ 算子兼容：NMS / GridSample / HardSwish 等要确认支持； 不支持时的标准做法——导出到 NMS 之前， NMS 放到（板上或PC上的）后处理里做 验证一步不能省： onnx.checker 过一遍 + onnxruntime 跑一张图， 与 PyTorch 输出对齐（误差 < 1e-3）才算导出成功。

讲解5. 板书⑤：RKNN 转换 + 量化（厂商工具链主场）

这一步是「厂商已经把量化做掉大半」的地方。你要理解配置项在干什么，然后把关两个关键点。

rknn-toolkit2：ONNX → .rknn rknn.config( target_platform="rk3576", mean_values=[[0,0,0]], std_values=[[255,255,255]], quantized_dtype="w8a8", int8 权重 + int8 激活 quantized_method="channel", per-channel（厂商默认） ) rknn.load_onnx("yolov8n.onnx") rknn.build(do_quantization=True, dataset="calib.txt") rknn.export_rknn("yolov8n_int8.rknn") 你真正要动手的：校准集（dataset） 一份列表文件，指向 100~500 张真实场景图片。 你不必手写量化算法 / 粒度——int8 per-channel 厂商已封装。 你只把关两件事： ① 校准集是否覆盖真实场景（分布对不对） ② 量化后 mAP 是否达标（掉幅在不在预算内）
预处理对齐（最容易被忽略、后果最严重） mean / std 与训练时不一致 → 输入分布错位 → 精度崩 letterbox 是否与训练一致（YOLO 用 letterbox 保持长宽比） RGB / BGR 通道顺序要一致 对齐一条口诀：训练怎么喂，转换就怎么配。

讲解6. 板书⑥：部署 + mAP 评估

转完不算完，要用数字验收。量化前 vs 量化后跑同一套 mAP，看「相对掉点」。

两个 mAP 口径 mAP@0.5 ：IoU 阈值取 0.5 下的平均精度（宽松，看"框住没有"） mAP@0.5:0.95 ：IoU 从 0.5 到 0.95（步长 0.05）取平均（严格，贴近实用） 验收要记录四个数 量化前 mAP、量化后 mAP、掉幅、单帧延迟 / FPS 例：mAP@0.5 0.42 → 0.40 （掉 2 个点，可接受） mAP@0.5:0.95 0.28 → 0.25 单帧 12 ms → 约 83 FPS（瑞芯微 3576 int8 参考量级） 掉点厉害时按顺序排查： ① 先怀疑校准集（分布是否覆盖真实场景） ② 预处理对齐（mean/std、letterbox、RGB/BGR） ③ 对回归头 / 敏感层保 fp16（混合量化）
mAP = 各类别 AP 在类别上的平均 · AP = PR 曲线下面积

讲解7. 板书⑦：CV 量化 vs LLM 量化差异

前面第 2 章讲过通用量化，这里用 CV 的口径再对一次——搞混了就会「LLM 那套调法用在检测上，mAP 掉一半」。

CV 量化 vs LLM 量化：目标不同，敏感点不同 CV 量化（检测/分割） LLM 量化 输入 图像（连续、空间相关） 文本 token（离散） 输出 bbox 坐标 + 掩码 / 类别 词表概率分布 关键头 回归头（做连续值回归） 最后 logits 层 量化最怕 回归头：连续值，误差直接进坐标 权重/激活里的 outlier 主流评估 mAP（检测）/ mIoU（分割） PPL（困惑度） 对齐手法 回归头 / 敏感层保高精度 权重分组 + 保护重要通道 一句话：CV 盯"坐标回归准不准"，LLM 盯"权重离群值"。

为什么回归头对量化更敏感、分类头相对鲁棒？用手算把差别算出来：

回归头 vs 分类头：量化噪声谁更能忍？ 设回归头输出归一化 bbox 坐标（0~1），int8 对称量化，qmax=127。 情形 A：动态范围正常，scale = 1/127 ≈ 0.00787 单坐标最大误差 = scale/2 ≈ ±0.0039 640px 图 → 0.0039 × 640 ≈ ±2.5 px → IoU 基本无损 情形 B：范围被别的输入撑大（outlier），scale = 5/127 ≈ 0.0394 误差 = ±0.0197 → 0.0197 × 640 ≈ ±12.6 px 20px 的小目标直接偏半个框 → mAP 掉一大截、小目标漏检 对比分类头：输出是"第几类"，只要 argmax 的最大项没被翻转， 结论就不变——量化噪声被"离散化"吃掉了 → 相对鲁棒。 结论：量化检测/分割，重点盯回归头与坐标/掩码精度； 量化 LLM，重点处理权重与激活的离群值。
评估指标别搞混（量化前后跑同一套，看"相对掉点"） CV ：mAP@0.5 / mAP@0.5:0.95（检测）、mIoU（分割） LLM ：PPL（困惑度）——预测下一个词有多"犹豫"，越大越差 CV 看绝对值掉几个点，LLM 看 PPL 的变化率。

本节要点回顾

  • CV 检测的端侧链路是六步：任务选型 → 数据标注 → 拿预训练模型 → 导出 ONNX → RKNN 转量化 → 部署与 mAP 评估。
  • CV 端侧成熟的原因是模型小、算子规整、预训练丰富、工具链支持好；多数场景只做「转换 + 量化」，不重训。
  • YOLO 结构分三段：backbone 抽语义、neck 融位置与语义、head 输出框与类别。
  • ONNX 导出的三个坑是 opset 版本、动态 shape、算子兼容；NMS 通常放在后处理。
  • RKNN 的 int8 per-channel 量化已由工具链封装，工程重点在「校准集覆盖真实分布」与「预处理对齐」。
  • 量化验收看 mAP@0.5 与 mAP@0.5:0.95 的相对掉幅，掉点首先怀疑校准集，其次考虑敏感层保 fp16。
  • CV 量化看 mAP/mIoU，LLM 量化看 PPL；回归头对量化最敏感，分类头相对鲁棒。

RK3576 特别提示

  • 3576 的 NPU 是 int8 定点加速器为主，CV 走 RKNN Toolkit（.rknn），不要用 rkllm——rkllm 只吃 LLM。
  • RKNN 的 int8 量化已是 per-channel，你无需手写量化算法；重心放在校准集与预处理对齐（mean/std、letterbox、RGB/BGR）。
  • 校准集务必覆盖夜景、小目标、强光/逆光、难例等真实场景，否则激活范围估偏，mAP 直接掉。
  • 回归头更敏感：必要时对回归头 / 敏感层保留 fp16（混合量化），别一刀切 int8。
  • ONNX 导出时固定输入 shape（如 1×3×640×640）最稳；NMS 放后处理，别塞进模型。
  • 板上性能与精度要一起记：单帧延迟参考量级约十几毫秒，具体以实测为准；验收以量化前后 mAP 掉幅为准绳。
