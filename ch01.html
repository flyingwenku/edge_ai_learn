课堂讲义（板书）

讲解0. 本节学什么

一句话：把「模型多大、占多少内存、跑多快」变成能心算的常识，同时先看清楚端侧 AI 到底在解决什么问题。

过去很多人是「跑一遍再决定」；但做端侧方案，你需要在买板子之前就说出：这个 3B 模型能不能塞进 RK3576、能跑多快、值不值得。这节课先给你全局图景，再练这张资源账本。

讲解1. 什么是端侧 AI

端侧 AI（Edge AI / On-device AI）：把模型的推理放在本地设备上跑，而不是把数据发到云端服务器算。这里的「设备」可能是手机、单板计算机（如 RK3576）、摄像头、车机、可穿戴、工业网关。

为什么要把推理放到端侧？四个动机 ① 低延迟：本地毫秒级响应，不受网络抖动影响 ② 隐私 ：原始数据（画面/语音）不出设备 ③ 离线 ：断网也能用，可靠性高 ④ 成本 ：省云侧算力与流量，边际成本≈0 代价：四个硬约束 内存小 、带宽低 、算力有限 、功耗有上限 → 所以端侧模型必须「小、省、快」，这正是量化与架构的全部由来

讲解2. 四类任务 / 模态概览

端侧落地常见的四类负载，瓶颈各不相同，不能一套调法打天下。先建立对照，后面章节会逐个展开。

模态典型任务一次推理的特征主要瓶颈关键指标
文本 LLM对话、摘要、意图识别自回归逐个 token（decode）内存带宽tok/s
图像 CV检测、分割、分类单次前向、像素量大算力 + 带宽mAP / mIoU / FPS
语音ASR 识别、KWS 唤醒连续音频帧、流式实时性 + 带宽WER / 唤醒率 / 延迟
传感器时序IMU / 振动 / 手势识别小模型、高频推理功耗 + 延迟准确率 / 功耗
一句话记住每类负载的「命门」 LLM ：慢在 decode 带宽——每吐一个字都要把权重读一遍 CV ：慢在 算力/带宽，且回归头对量化敏感（框会飞） 语音 ：难在流式与实时——要边听边出，不能攒完再算 时序 ：难在功耗——常驻后台，模型要极小极省

讲解3. 资源三角：内存 / 带宽 / 算力

端侧的一切取舍，都绕不开这三样。它们互相制约，你不可能同时把三者都拉满。

资源三角 内存 → 决定「装不装得下」：权重 + KV Cache + 激活 + 框架开销 带宽 → 决定「算多快」：decode 每步都要读一遍权重 算力 → 决定「能不能算」：TOPS 决定 prefill / 单次前向的耗时 相互制约： 精度 ↑ → 内存 ↑（同一模型占用更大） 模型 ↑ → 带宽压力 ↑（每步要读更多权重） 并发 ↑ → 内存、带宽、算力三者同时吃紧 端侧第一原则：先算内存能不能装下，再看带宽跑多快，最后才谈算力。

讲解4. 端侧 vs 云端的取舍

端侧不是「什么都自己扛」，而是和云端分工。先把两边的边界画清楚：

维度端侧云端
延迟低（本地毫秒级）受网络影响，波动大
隐私原始数据不出设备数据需上传
离线可用断网即不可用
成本一次性硬件投入按量计费 + 带宽成本
可跑模型受内存/算力限制（1B~7B 级）可跑超大模型
更新需 OTA / 重刷服务端随时更新
分工原则：高频、低延迟、隐私敏感的任务放端侧；需要超大模型/复杂推理的任务回退云端。端侧常用 1.5B~3B 做本地意图识别与简单对话，复杂问题再上行。这条分工线会在后续「系统与架构」部分（第 15、16 章）展开成完整方案。

讲解5. 板书①：位数 → 字节（精度的第一笔账）

建立资源账本的第一条换算：1 Byte = 8 bit。把「每个参数多少位」除以 8 就是字节数。

精度 位数 ÷8 每参数字节 ───────────────────────────────────────────── fp32 32 bit → 32/8 = 4.0 Byte fp16 16 bit → 16/8 = 2.0 Byte bf16 16 bit → 16/8 = 2.0 Byte int8 8 bit → 8/8 = 1.0 Byte int4 4 bit → 4/8 = 0.5 Byte ← 关键 int4 = 0.5 字节：因为 4 位装不下 1 个字节， 所以硬件把 2 个参数打包进 1 个字节（叫 packed）。 这就是为什么「4 位」听起来像省了一半，其实是省到 1/8。
bf16 vs fp16（只记结论，不推公式）：字节数一样（都是 2B）。fp16 精度细但范围窄、容易溢出；bf16 范围大、更稳，现代大模型/端侧更偏好 bf16。选型时默认 bf16 就对了。

讲解6. 板书②：内存公式 + 手算示范

权重内存 ≈ 参数量 × 每参数字节

注意「≈」，因为真实占用总比净值大一点（下面解释）。先看一个完整手算：

示范：3B 模型放 int4 要多少内存？ 第一步 净值： 3,000,000,000 个参数 × 0.5 Byte = 1,500,000,000 Byte = 1.5 GB（净权重） 第二步 真实： ×1.2 ~ 1.4 的 overhead ≈ 1.5 × 1.3 = 约 2 GB ← 这就是「3B int4 约 2GB」的来历 为什么有 overhead？ ① Embedding 表通常不量化（或单独 int8），体积不小 ② LayerNorm / bias 这类小张量一般留高精度 ③ 内存对齐、runtime 缓冲、框架自身开销 经验值：int4 真实占用 ≈ 净值 × 1.3，工程上直接取整背整数。

讲解7. 板书③：带宽 → tok/s（三档口径）

这是本章的灵魂。大模型生成文字时（decode），每吐 1 个 token，NPU 都要把整个模型权重从内存里读一遍。所以速度不由算力决定，由内存带宽决定。

tok/s ≈ 有效带宽 ÷ 模型真实占用(GB)
示范（RK3576，LPDDR5-4800、32-bit，带宽三档） 理论峰值 ≈ 19 GB/s （4800 MT/s × 4 B ≈ 19.2） NPU 独占实测 ≈ 12~16 GB/s（无视频解码/ISP/GPU 渲染） 产品真实场景 ≈ 7~11 GB/s （摄像头 + NPU + 屏幕同开，带宽被抢） 3B int4： /2.0GB → NPU 独占 6~8 tok/s ；产品 3.5~5.5 tok/s 7B int4： /4.5GB → NPU 独占 2.7~3.6 tok/s；产品 1.6~2.4 tok/s 为什么产品实测只有几 tok/s，远低于理论峰值？ ① 产品里带宽被摄像头/ISP/屏幕瓜分，有效带宽只剩 7~11 GB/s ② KV Cache 也在抢带宽（第 8 章细讲） ③ kernel 调度、算子切换有开销 ④ 有些算子没跑到 NPU，掉回 CPU
一句话记住：算力决定「能不能算」，带宽决定「算多快」。LLM 聊天场景默认是带宽瓶颈——这句话后面每章都用得上。

本节要点回顾

  • 端侧 AI 把推理放在本地设备，换来低延迟、隐私、离线、低成本，代价是内存、带宽、算力、功耗四重约束。
  • 端侧常见四类负载：文本 LLM（decode 带宽瓶颈）、图像 CV（算力+带宽、回归头对量化敏感）、语音（流式与实时）、传感器时序（小模型、低功耗）。
  • 资源三角：内存决定「装不装得下」，带宽决定「算多快」，算力决定「能不能算」；三者相互制约。
  • 精度换算：1 字节 = 8 位；int4 = 0.5 字节（两个参数打包进一个字节）。
  • 内存账本：权重内存 ≈ 参数量 × 每参数字节；工程真实占用 ≈ 净值 × 1.3。
  • 带宽账本（RK3576 / LPDDR5-4800 32-bit）：理论峰值 ≈ 19 GB/s，NPU 独占 12~16 GB/s，产品场景 7~11 GB/s。
  • tok/s ≈ 有效带宽 ÷ 模型真实占用（GB）；LLM 聊天场景默认是带宽瓶颈，不是算力瓶颈。

RK3576 特别提示

  • 带宽分三档：理论峰值 ≈ 19 GB/s（LPDDR5-4800 × 32-bit），NPU 独占实测 12~16 GB/s，产品真实场景（摄像头 + NPU + 屏幕同开）只剩 7~11 GB/s。产品落地要看最后一档，「3B int4 只有 3.5~5.5 tok/s」才是真实数字。
  • 16GB 内存不代表能装大模型——留给系统、KV Cache、多进程的空间要扣掉，实际安全预算约 8~12GB。
  • 3576 的 NPU 是 6 TOPS int8；int4 通常靠 int8 模拟或特定算子支持，第 2 章会讲怎么选量化方案、第 13~14 章部署调优时会验证，本章先按理论算。
