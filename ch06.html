课堂讲义（板书）

讲解0. 这节课到底学什么

第 4 章你搞懂了注意力。但注意力量只占参数的一小部分——真正"装参数、装知识"的是 FFN。这一章你搞清 FFN 和 MoE，再看清整个架构大方向（Transformer / SSM / 混合），最后拿到一张端侧主流模型清单。面试高频题：给一个端侧场景，你选什么架构、用什么模型？

讲解1. 板书①：FFN——Transformer 的"知识仓库"

每个 Transformer 层有两个子块：注意力 + FFN。注意力负责"搬运"，FFN 负责"记忆"。

FFN = Feed-Forward Network（前馈网络） 结构：d → 4d → d （两层线性 + 一个激活函数） 中间隐藏层宽度通常是输入的 4 倍 （现代模型用 SwiGLU，实际约 8/3 倍，这里按 4d 讲，便于手算） 参数量公式（两层矩阵） W1: d × 4d W2: 4d × d 合计 = 2 × 4d² = 8d² 手算：d = 2048 的单层 FFN 8 × 2048² = 8 × 4,194,304 = 33.6M 参数/层 36 层 → 33.6M × 36 = 约 1.21B 对比同模型的注意力层（GQA） Q: d×d = 4.19M K,V: d×(2×128) = 0.52M 各 O: d×d = 4.19M 合计 ≈ 9.4M/层 → 36 层 ≈ 0.34B
结论：FFN 参数 ≈ 注意力的 3~7 倍 3B 这类小模型里，约 2/3 的参数在 FFN。 FFN 到底在干什么：知识存储 研究共识（ROME、知识编辑等工作）： · 注意力 = "token 之间搬运/聚合信息"（路由） · FFN = "把知识写进权重里"（记忆 / 查表） 所以： 模型"知道多少" ← 主要由 FFN 决定 模型"会不会用上下文" ← 主要由 注意力 决定 直觉：FFN 像一个巨大的 key-value 记忆库， 每个神经元近似"匹配某种特征 → 输出某条知识"。 模型越大越"博学"，主要就是 FFN 堆得多。
一句话：注意力管"看关系"，FFN 管"记知识"。所以量化时 FFN 权重占大头，也是 KV Cache 之外最大的内存来源。

讲解2. 板书②：MoE——稀疏激活原理 + 手算

MoE = Mixture of Experts（混合专家） 核心想法：把 1 个 FFN 换成 N 个"专家 FFN"， 每个 token 只走其中 top-k 个（其余专家不参与计算）。 · 总参数量 = N × 8d² （所有专家都要存进内存！） · 激活参数量 = k × 8d² （每个 token 实际算的） 关键区别（面试点） 计算量由"激活参数"决定 → 稀疏 → 省算力 内存占用由"总参数量"决定 → 很大 → 不省内存 举例：Mixtral 8×7B 8 个专家，top-2 路由 总参数 ≈ 47B，激活 ≈ 13B → 算力只花 13B（便宜），但要存 47B（贵） 另一端：DeepSeek-V3 总 671B / 激活 37B → 推理算力极省，但内存得按 671B 级别准备 一句话：MoE 用"更大的总内存"换"更小的单次算力"。
MoE 的本质取舍：它把"算力"和"内存"解耦了——用稀疏激活省算力，代价是总参数量（内存）反而更大。谁的内存便宜、算力贵，谁就用 MoE → 那是云端，不是端侧。

讲解3. 板书③：为什么端侧少用 MoE

这是本章最重要的判断，四个硬伤，逐个讲：

为什么端侧基本不用 MoE？四个硬伤 ① 内存装不下（最直接） Mixtral 47B，即便压到 int4 也 ≈ 24 GB RK3576 内存上限 16 GB → 装不下。 端侧要的是"总参数小"，MoE 天生总参数大。 ② batch=1 时 MoE 不省时间（最关键！） decode 阶段是带宽瓶颈：每生成 1 个 token，要把权重读一遍。 MoE 只激活 k 个专家 → 少算，但权重还是得从内存读（而且读得更碎）。 省算力 ≠ 省带宽 → 单用户场景几乎没收益。 只有大 batch（云端、多用户）才把 MoE 的稀疏优势吃满。 ③ 调度开销 路由 + 动态 shape + 专家分散 → NPU/框架对小算子、动态分支不友好。 ④ 随机访存 路由后读的是"分散在不同地址"的专家权重 → 带宽利用率更低， 对 3576 这种带宽本就紧张的板子雪上加霜。 一句话：MoE 是"云端多用户"的省算力方案； 端侧单用户、带宽受限 → 用密集小模型 + GQA 更实在。
最容易背错的一点："MoE 省算力"没错，但在端侧单用户推理里，瓶颈是带宽不是算力，而 MoE 一点都不省带宽（总权重还是那么多，读的还是分散的）。所以 MoE 对端侧 decode 几乎没有加速收益。

讲解4. 板书④：Transformer vs SSM(Mamba) vs 混合

范式计算复杂度推理内存长文本召回/复制NPU 成熟度
TransformerO(n²)随 n 增长（KV Cache）一般强高
SSM / MambaO(n)常数（无 KV）好弱低
混合架构O(n)~O(n²)小好强（有注意力层）中
SSM / Mamba 是什么（一句话） 用"状态空间模型"逐 token 递推：h_t = A·h_{t-1} + B·x_t 像 RNN 一样，只维护一个固定大小的状态 → 内存不随上下文增长。 代价：状态"挤"不下太多历史 → 精确回忆/复制能力弱于注意力。 混合架构：两头都要 大部分层用 SSM（省内存、长文本好），少量层插注意力（保住召回）。 代表：Jamba、Zamba、NVIDIA Hymba、Qwen3-Next、MiniCPM 的部分版本。 端侧意义 SSM 的"常数内存"对内存吃紧的板子很有吸引力（终于不怕长上下文爆内存）。 但 NPU 对 SSM 的递推 scan 支持还不成熟 → 目前落地仍以 Transformer + GQA 为主，SSM 作为观察方向。
架构师结论：端侧现在选 Transformer + GQA（生态成熟、NPU 支持好）；Mixed/SSM 作为 2026 之后的长上下文储备，关注别踩坑（算子支持）。

讲解5. 板书⑤：端侧主流模型盘点

模型常见规模特点端侧适配许可
Qwen2.50.5 / 1.5 / 3 / 7B中文强、生态全、GQA + RoPE好（RKNN 有官方示例）Apache-2.0
MiniCPM2.4B / 4B小尺寸强、端侧导向、多模态版好开源（部分需授权）

端侧选型口诀（按任务挑规模） 意图识别 / 分类 / 短语槽位 → 0.5B ~ 1.5B（int8 即可） 简单对话 / 摘要 / RAG 生成 → 1.5B ~ 3B（int8 或 int4） 复杂推理 / 代码 → 大概率走云端，端侧只兜底 首选 Qwen2.5-1.5B/3B：中文好、GQA、RKNN 官方示例齐全， 落地风险最低（这是"能用现成的就别自己造"的工程选择）。
记忆锚点：端侧选型 = 任务复杂度 → 规模 → 量化 → 生态支持。前两步看需求，后两步看板子，最后一步看"有没有现成的 RKNN 示例"。

RK3576 特别提示

  • 3576 内存上限 16GB，MoE 模型（如 Mixtral 47B）根本装不下，架构评审时直接排除。
  • 端侧 decode 是带宽瓶颈，MoE 的稀疏优势在 batch=1 场景吃不到，别被"省算力"忽悠。
  • 选模型优先看是否 GQA + 是否有 RKNN 官方示例（Qwen2.5 / MiniCPM 最省心）。
  • SSM/混合架构作为长上下文储备观察，但落地前先确认 NPU 算子支持，别踩"跑不起来"的坑。
