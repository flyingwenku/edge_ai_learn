课堂讲义（板书）

讲解0. 这节课到底学什么

第 1~2 章你在纸上算：模型多大、用哪种量化、多少 tok/s。但架构师不能只会算，还得真的把模型塞进 NPU。这一步 90% 的人会翻车——不是报错就是精度崩，原因几乎都出在校准集和量化配置上。

你要能三件事：① 说清整条转换流水线每一步在干嘛；② 用一份配置把模型转出来并跑通；③ 量化前后精度差多少、差到什么程度就不能上线。

讲解1. 板书①：整条流水线（HF → ONNX → RKNN → .rknn）

NPU 不认识 PyTorch，只认识瑞芯微自己的 .rknn。所以中间要有「翻译」：先把 PyTorch 换成通用格式 ONNX，再由 rknn-toolkit2 编译成 .rknn。

端侧 LLM 转换流水线（四段） ① 原始权重 HuggingFace / PyTorch (.safetensors) │ 取到模型 + tokenizer ▼ ② 转换准备 ONNX 导出 / 直接喂 rkllm 的权重转换脚本 │ 小模型走 onnx → rknn-toolkit2 │ LLM 走 rknn-llm（rkllm）一键转换 ▼ ③ 量化 + 编译 rknn-toolkit2 / rkllm │ build(do_quantization=True, dataset=校准集) ▼ ④ 产物 .rknn （NPU 直接加载，与硬件绑定） 关键：.rknn 是"过编译"的——它针对目标平台（rk3576） 做过算子映射和量化，换个平台要在新平台重转。 所以 target_platform 一定要写对。

两条路线怎么选：小模型/ViT 走 onnx + rknn-toolkit2；LLM 走 rknn-llm（rkllm），它内部封装了量化与权重打包，一条命令出 .rkllm。

讲解2. 板书②：量化配置三件套

PTQ（训练后量化）能不能成，就看这三个参数。少一个都跑不起来，配错任何一个精度就崩。

三件套 —— 缺一不可 ① dataset（校准集） 必须给，且要真实 作用：让量化器"看"一遍真实输入，统计每个张量的动态范围 形态：rknn-toolkit2 用小样本 bin/npy； rkllm 用一段真实 prompt 文本 ② quantized_dtype（量化类型） 告诉编译器：权重几位、激活几位 w8a8 权重 8 / 激活 8 → 最稳，3576 首选 w8a16 权重 8 / 激活 16 → 精度更高，慢一些 w4a16 权重 4 / 激活 16 → LLM 端侧主流，省内存 ③ quantized_algorithm（量化算法） normal 最直接（max 定标），快、够用 mmse 最小化量化误差，慢一点、精度更好 kl_divergence 分布对齐，对激活敏感场景好 一句话：dtype 决定"多省"，algorithm 决定"多准"。
rkllm 转换配置示例（config.json） { "target_platform": "rk3576", "model_path": "Qwen2.5-3B-Instruct", "quantized_dtype": "w4a16", // 权重 4 位，激活 16 位 "quantized_algorithm": "normal", "num_npu_core": 1, "group_size": 128 } rknn-toolkit2（小模型）等价写法 rknn.config(quantized_dtype='w8a8', quantized_algorithm='mmse', optimization_level=3) rknn.build(do_quantization=True, dataset='dataset.txt')

讲解3. 板书③：校准集怎么做（决定成败）

量化的本质是「给每个张量找一把尺子」。尺子的量程由校准数据决定——你喂什么，它就以为世界长什么样。喂错，线上就崩。

校准集三条军规 ① 要真实 用产品里真实的输入分布。 聊天模型 → 用真实用户问答；别用随机噪声。 用随机数据校准 = 上线后精度崩的头号原因 ② 要够量 LLM：100 ~ 500 条代表性 prompt； 视觉小模型：100 ~ 500 张真实图片。 太少 → 统计不稳；太多 → 转换慢，收益递减。 ③ 要覆盖 长度覆盖短/中/长（如 64 / 512 / 2048 tok）； 内容覆盖你的真实任务（客服/翻译/代码都要有样本）。 dataset.txt 长这样（每行一条样本文件路径） calib/sample_000.bin calib/sample_001.bin ... （LLM 路线则直接给一个 prompts.txt，每行一句真实问题）
面试加分点：「校准集不是随便凑几百条，要匹配线上输入分布，长短和任务类型都覆盖，否则 outlier 会把某些层 scale 撑大、整层精度塌。」

讲解4. 板书④：量化前后精度怎么比（PPL + 人肉）

架构师不看「感觉变笨了」，要看数字。语言模型最通用的是困惑度 PPL：模型对下一 token 有多「困惑」，越低越好。

PPL = exp( −(1/N) · Σ ln p(wᵢ) )

先看手算，再套到量化对比上：

手算：5 个 token 的概率 p = [0.8, 0.6, 0.9, 0.5, 0.7] ln p = [-0.2231, -0.5108, -0.1054, -0.6931, -0.3567] Σ ln p = -1.8891 平均负对数似然 = 1.8891 / 5 = 0.3778 PPL = exp(0.3778) = 1.459 量化后同位置概率变成 p' = [0.7, 0.5, 0.8, 0.4, 0.6] Σ ln p' = -2.7001 → 平均 = 0.5400 PPL' = exp(0.5400) = 1.716 ΔPPL = 1.716 − 1.459 = 0.257 → 相对 +17.6% 经验判据（语言模型）： PPL 涨幅 < 5% → 放心上线 5% ~ 10% → 抽样人肉看，多半可接受 > 10% → 危险，换 w8a16 或调校准集

人肉对比（PPL 之外的必做项）：固定 20 个真实问题，原始模型和量化模型各答一遍，记录「是否跑题 / 是否重复 / 是否截断 / 是否答对」。表格存档，这是给产品经理看的东西。

人肉对比记录表（模板） # | 问题 | 原始质量(1-5) | 量化质量(1-5) | 现象 ---|-------------|--------------|--------------|---------------- 1 | 北京天气？ | 5 | 5 | 一致 2 | 算 17×23 | 5 | 3 | 量化后算错 3 | 写首五言诗 | 4 | 4 | 少一句 ... 统计：平均分差 > 0.5 或出现"事实错误"≥2 条 → 不能上线。

讲解5. 板书⑤：三个调优旋钮 + 带宽利用率

精度/速度不达标时，按下面顺序调。别瞎改，一次动一个变量。

旋钮一览（按性价比排序） ① group_size（int4 专用） 常见 32 / 64 / 128 小 → 组内更精细、精度更高，但 scale 开销↑ 128 是默认甜点（回顾第 2 章：开销仅 ~3%） ② 校准数据 换更贴近线上、覆盖更全的样本 性价比最高的一招，往往比调算法管用 ③ NPU 核心数 num_npu_core 3576 是单核 6 TOPS（3588 才三核）； 3576 上固定 1，调它没意义；迁 3588 时才有 1/2/3 可选 带宽利用率（判断跑没跑满的关键指标） decode 实测 8 tok/s，模型 int4 3B ≈ 2.0 GB 有效带宽 = 8 × 2.0 = 16 GB/s 利用率 = 16 / 35 = 45.7% → < 60% 说明没跑满，还有调优空间（batch/算子）
一句话记住：带宽利用率 = tok/s × 模型真实GB ÷ 35。它是判断「瓶颈在带宽还是在别处」的尺子，比单纯看 tok/s 有用得多。

讲解6. 板书⑥：上线判断（本章结论）

能不能上线？三关过完才敢点头 ① 精度关 PPL 涨幅 <5% 且人肉对比无事实错误 ② 性能关 tok/s 达产品延迟目标（如 > 8 tok/s） 且带宽利用率 ≥ 60%（说明已榨干带宽） ③ 稳定关 连续对话 30 分钟不 OOM、不崩、显存/内存平稳 三关全过 → 可以上线 任一不过 → 回退方案：w4a16 → w8a16，或换校准集重转 被问「这个量化方案能不能上线」→ 标准答： 「我按三关判：PPL 涨幅、人肉对比、带宽利用率与稳定性。 3B w4a16 若 PPL 涨幅 <5%、实测 >8 tok/s、利用率 ≥60%、长跑不 OOM、 人肉无事实错误——就上线；否则退 w8a16 或补校准集重转。」

讲解7. 板书⑦：ONNX 算子排坑（PyTorch → ONNX → RKNN）

量化是「转换」的后半程，前半程是算子能不能转过去。NPU 只认一套固定的算子集，PyTorch 里花哨的写法往往在导出 ONNX 或编译 RKNN 时炸掉。报错看似杂乱，其实就三类。

转换链路：PyTorch → ONNX → RKNN（三段都要过） PyTorch(.pt/.safetensors) │ torch.onnx.export / zoo 的导出脚本 ▼ ONNX(.onnx) ← ① 算子是否都被 ONNX 支持？opset 版本对不对？ │ rknn-toolkit2: load_onnx → build ▼ RKNN(.rknn) ← ② 算子是否都被 NPU 支持？shape 是否静态？ 三段各有各的坑，报错信息不一样，要对号入座。
三类高频报错 → 定位 → 处理 ① 不支持的算子（Unsupported operator: XXX） 现象：ONNX 里带了自定义 / 冷门算子（如特殊 GridSample、 deform conv、自定义 attention、非标 Reduce）。 定位：Netron 打开 .onnx 看节点类型；或看 build 日志的算子名。 处理：用等价标准算子重写；或把不支持的算子拆成 NPU 支持的基础算子组合（如特殊激活拆成 mul/add/sigmoid）。 ② opset 版本不匹配（opset version not supported） 现象：导出用了 opset 17+，工具链只吃到 11~13；或算子语义随 opset 变化（如 Resize / Slice 的属性名改了）。 定位：onnx.load 后读 model.opset_import。 处理：导出时显式钉住 torch.onnx.export(opset_version=12)； 或用 onnx.version_converter 把模型降到目标 opset。 ③ 动态 shape（dynamic shape / -1 dims） 现象：batch 或序列长度是 -1，NPU 编译期定不了内存布局。 定位：Netron 看输入 / 中间张量的 dim 是不是 -1。 处理：导出时固定 shape（dynamic_axes 留空）；LLM 变长序列 用固定 max_seq_len 导出，或走 rkllm（内部已处理 KV Cache 布局）。 通用心法：报错先问「是 ONNX 不支持，还是 NPU 不支持」—— ONNX 阶段报错 → 改导出；RKNN 阶段报错 → 换/拆算子或固定 shape。
排坑顺序：先用 onnx.checker 确认 ONNX 本身合法，再上 Netron 数算子，最后才 build。别一上来就 build——报错信息会混在一起，定位成本翻倍。

讲解8. 板书⑧：RKNN 算子支持与回退（量产最常见的坑）

NPU 是专用电路，只实现了一部分算子。编译时工具链会把每个算子映射到 NPU；映射不上的就「回退（fallback）」到 CPU 执行。功能上照样算对——但性能会断崖式下跌，这是 RKNN 项目量产翻车的第一名。

为什么会暴跌？——数据搬运才是元凶 NPU 算 3 层 → 回退 1 层 CPU → 再回 NPU 算 5 层 → 又回退 ... 每次 NPU ↔ CPU 切换，张量要： ① 从 NPU 内存搬回 CPU 内存 ② CPU 算完再搬回 NPU 搬运量 = 该张量大小，走的是有限的片外带宽（3576 仅 ~35 GB/s） 一次特征图搬运 = 几十 MB → 十几毫秒； 回退层多起来，decode 速度可以从 15 tok/s 掉到 3 tok/s。 更糟的是：回退常常落在「每个 block 都有」的算子上， 导致 NPU/CPU 反复横跳，搬运开销 ×层数，直接吃掉全部收益。
怎么查「哪些算子支持」 · rknn-toolkit2 文档：算子支持列表（op support list）， 逐一列明每个算子在各平台的 NPU / CPU 归属； · build 日志：搜 not supported / fallback / cpu， 工具链会打印哪些节点被放到 CPU； · rknn_model_zoo 对应模型的 README：官方已标注已知回退点与规避法。
怎么避免回退（按优先级） ① 选「已在 zoo 里跑通」的模型结构——别人踩过的坑别再踩。 ② 替换不支持的算子：用 NPU 支持的基础算子等价重写 （如 GELU → 近似 tanh 形式；特殊 Norm → 标准 LayerNorm）。 ③ 融合 / 改写结构：把诱发回退的动态分支改成静态等价实现。 ④ 固定 shape：动态 shape 常直接判给 CPU（见板书⑦）。 ⑤ 改量化配置重试：某些算子在 w8a16 下能被 NPU 接纳，w4a16 不行。 验收口径：build 日志里 fallback 条目为 0， 且 profiling 显示算子几乎全在 NPU 上。
一句话记住：回退不是「能不能跑」的问题，是「跑不跑得动」的问题。功能上给你算对，性能上直接把你打回原型——量产前必须清干净。

讲解9. 板书⑨：NPU/CPU 混合调度与 profiling（把回退揪出来）

完全不回退很难，架构师要做的是把回退控制在可控范围：该上 NPU 的上 NPU，天然属于 CPU 的交给 CPU，且尽量让同一段计算留在同一侧，减少搬运。

哪些层适合 NPU / 哪些适合 CPU 放 NPU（算力密集、数据并行） · 大矩阵乘（QKV / FFN / 输出投影） · 卷积 / 常规激活 / 逐元素乘加 · LayerNorm（标准形式） 放 CPU（控制逻辑、轻量、串行依赖） · tokenizer / detokenizer · sampling（top-k / top-p 采样，含随机数） · RoPE 角度计算、KV Cache 索引等零碎控制流 · 动态 shape / 数据依赖的分支 原则：让 NPU 干重活，CPU 干调度； 同一段计算尽量不跨设备——跨一次 = 一次搬运。
用 profiling 看出回退 rknn-toolkit2 的 eval_perf / rknn.eval_perf() 会输出： · 每个算子的耗时 · 每个算子跑在 NPU 还是 CPU · 总耗时里 NPU / CPU / 搬运各占多少 怎么读这份 profiling · CPU 占比 > 20% 或个别算子耗时异常 → 十有八九是回退； · 某个小算子耗时比大矩阵乘还长 → 它就在 CPU（还带搬运）； · 结合 build 日志的 fallback 列表，一一对应定位。 板端交叉验证 · cat /sys/kernel/debug/rknpu/load → NPU 利用率低 = 没吃饱； · top 看主进程 CPU% → CPU 长期 100%+ = 在替 NPU 干活。
闭环排障：profiling 定位「哪个算子掉 CPU」→ 回板书⑧ 用等价替换 / 固定 shape 消掉它 → 重跑 profiling 确认 CPU 占比下降。改一个、测一次，别一次改一堆。

profiling 找算子回退（新增）

目标
跑一次 rknn/llm profiling，找出掉到 CPU 的算子，并给出规避方案。
要掌握
build 日志里的 not supported / fallback；eval_perf 输出怎么读；CPU 占比与搬运的关系。
实操步骤
① build 时保留完整日志，grep not supported|fallback|cpu 存成 fallback_list.txt；② 用 rknn.eval_perf() 或板端 profiling 跑一遍，导出每算子耗时与设备归属；③ 挑出耗时异常的 CPU 算子，写 fallback_report.md：算子名 / 原因 / 等价替换或固定 shape 方案 / 重测后的 CPU 占比。
检验标准
能列出至少 1 个回退算子，给出可行规避方案，并用重跑数据证明 CPU 占比下降（或 fallback 归零）。

当日产出（要落盘）

  • pipeline.md —— 四段转换流水线图 + 每步命令。
  • calib/prompts.txt —— 200 条真实校准 prompt（覆盖长短与任务类型）。
  • quant_config.md —— w8a8 / w8a16 / w4a16 三档配置对比与默认结论。
  • build.sh / build_rknn.py + build_log.txt —— 真实转换脚本与日志。
  • ppl_eval.py + ppl_compare.md + human_eval.md —— 量化前后精度对比。
  • quant_deploy_report.md —— 端侧量化部署报告（一页，核心产出）。
  • fallback_list.txt + fallback_report.md —— 算子回退定位与规避（profiling）。

检验标准（自测）

  • 能说清「量化配置三件套」分别是什么、少哪个会怎样。
  • 能解释「为什么校准集不能用随机数据」。
  • 会用 PPL 涨幅 <5% / 5-10% / >10% 判据给精度下结论。
  • 会算带宽利用率（tok/s × 模型GB ÷ 35），并判断是否跑满。
  • 给「这个量化方案能不能上线」能按「精度关 / 性能关 / 稳定关」三关作答。
  • 能说出 ONNX 三类高频报错（不支持算子 / opset 不匹配 / 动态 shape）的定位与处理。
  • 能用 build 日志与 profiling 判断哪些算子回退到 CPU，并说清为什么搬运会拖垮性能。

面试话术

可直接背

「端侧量化部署我走 rknn-toolkit2 / rkllm：先导出权重，再给一份匹配线上分布的校准集做 PTQ，量化配置三件套是 dataset、quantized_dtype、quantized_algorithm——dtype 决定多省、algorithm 决定多准，3576 上我默认 w4a16 + normal，group_size 128。转完我会量化前后对比：算 PPL，涨幅控制在 5% 以内，再做一轮 20 题人肉对比确认没有事实错误；性能上看带宽利用率，tok/s 乘模型大小除以 35GB/s，到 60% 以上才算榨干带宽。三关都过我才判断可以上线，否则回退 w8a16 或换校准集重转。」

能力标签：能把模型真正转成端侧可用产物，并用数字判断量化方案是否可上线——端侧量化部署能力。

RK3576 特别提示

  • RK3576 的 NPU 是 单核 6 TOPS，num_npu_core 固定为 1；「试核心数」是 RK3588 三核才有的玩法，3576 上调它没意义。
  • 3576 以 int8 定点加速为主，w4a16 多为 int8 模拟或部分算子支持——转完务必实测 tok/s 和精度，别想当然。
  • LLM 走 rknn-llm（rkllm） 一键转换，比手搓 ONNX 稳；小模型/ViT 才用 rknn-toolkit2。
  • target_platform 必须写 rk3576；换板子要重转，产物不通用。
