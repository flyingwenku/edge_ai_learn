课堂讲义（板书）

讲解0. 这节课到底学什么

前面你已经有：量化（能算内存）、部署（能跑起来）、RAG 思路、端侧调优。但面试官不看零件，只看成品。本章把零件收口成一个可演示的 agent，并产出一份架构设计文档。记住这条判据：文档的价值不在「写了什么」，而在「每个选择你都能说出为什么不选另一个」。

讲解1. 板书①：function calling——让本地模型会「用工具」

本地模型只会说话不够，架构师要让它能干活：查天气、设闹钟。做法就是 function calling 最小闭环——模型只负责「吐结构化请求」，真正执行永远在本地代码手里。

本地工具调用（function calling）最小闭环 ① 注册工具 schema（给模型看的「菜单」） tools = [ {"name":"get_weather","desc":"查某城市天气","params":{"city":"str"}}, {"name":"set_alarm","desc":"设定闹钟","params":{"time":"HH:MM","label":"str"}} ] ② 模型输出 结构化调用请求（不是自然语言！） 用户：「明天几点下雨？顺便 7 点叫我」 模型 → {"tool":"get_weather","args":{"city":"本地"}} 模型 → {"tool":"set_alarm","args":{"time":"07:00","label":"起床"}} ③ 本地执行器：解析 JSON → 跑本地函数 → 结果回填 → 二次生成 执行(get_weather) → {"temp":18,"rain":"14:00"} → 塞回 prompt → 组织成人话 关键：模型不接触真实系统，调用请求经本地代码校验后才执行。 安全、可控、断网也能跑（工具本身是离线的）。
一句话结论：function calling 的本质是「让模型吐 JSON，而不是吐散文」；执行权、校验权、权限永远留在本地代码里——这正是端侧架构师的掌控点。

给分不清「工具描述、约束、兜底」的写法补一条模板：

工具 schema 写法模板 { "name": "set_alarm", "description": "设置一个本地闹钟", ← 越具体，模型越少乱调 "parameters": { "type":"object", "properties":{ "time":{"type":"string","description":"24 小时制 HH:MM"}, "label":{"type":"string","description":"闹钟名称，可空"} }, "required":["time"] } } 兜底：解析失败 / 参数非法 → 不执行，回一句「我没听清，你再说一遍」。 宁可让模型说「我不确定」，也不让它乱调工具。

讲解2. 板书②：本地 RAG——轻量向量库 + 检索闭环

模型不知道你的私域知识（产品手册、内部文档）。本地 RAG 让它「开卷考试」，且全程离线。流程就两步：离线建库 + 在线检索。

本地 RAG 最小闭环（离线、无外网） ① 离线建库（一次性，跑在 PC 上） 文档 → 切块 chunk（300~500 字，重叠 50）→ 向量化 embedding → 写入本地向量库 → 建索引 ② 在线检索（每次提问，跑在端侧） 问题 → 向量化 → 向量库 top-k 相似 chunk（k=3~5） → 拼进 prompt → 本地 LLM 生成带引用的答案 轻量向量库选型（端侧内存优先） sqlite-vec ：单文件、零依赖、可嵌入，首选 FAISS(CPU) ：快，但要单独带库 chroma 本地态：开发方便，端侧偏重 内存预算：几万条 chunk 的索引 ≈ < 50MB，完全塞得下。 额外开销：embedding 模型也要端侧化（可用小模型，如 bge-small 量化版）。
一句话结论：RAG = 「检索」+「生成」两步；本地 RAG 的难点不是向量库，而是把 embedding 模型也压到端侧能跑，并把索引内存控制在几十 MB。

讲解3. 板书③：性能测试四件套（端侧 LLM 的体检表）

没有数据的架构文档是散文。端侧 LLM 的性能就测四样，每一样都对应一个用户体感或一个硬件瓶颈。

性能测试四件套 ① 首 token 延迟 TTFT：提交到吐出第 1 个字 → 体感「快不快」 ② 生成速度 tok/s ：稳定阶段每秒 token → 体感「流不流畅」 ③ 内存峰值 RSS ：运行最高占用 → 决定「塞不塞得进」 ④ NPU 利用率 ：NPU 是否吃满 → 判断瓶颈在算力还是带宽 测量模板（每次必须记录环境，否则数据没用） 模型=/量化=/上下文长度=/线程数=/温度= TTFT=___ms tok/s=___ RSS=___MB NPU=___%

怎么用这四个数下结论？看一条推理：

用数据定位瓶颈（面试可直接讲） 3B int4 权重 ≈ 2GB 每生成 1 token 需读一遍权重：2GB RK3576 内存带宽 ≈ 35 GB/s 理论 tok/s = 35 / 2 ≈ 17 tok/s 实测 = 5~10 tok/s 结论：算力没吃满、NPU 利用率不高 → 瓶颈是内存带宽，不是 NPU。 优化方向：降比特（更狠量化）、减上下文、增加前缀缓存，而不是堆算力。
一句话结论：端侧 LLM 的性能瓶颈通常是内存带宽而非算力；四个指标一起看，才能判断该往「量化 / 上下文 / 缓存」哪个方向优化。

讲解4. 板书④：架构设计文档模板（一页纸 ADR）

架构文档别写成长篇报告，用 ADR（Architecture Decision Record）思路：一页讲清七件事。这是本章的核心产出。

《架构设计文档》一页纸模板 1. 背景与目标 ：要解决什么问题、给谁用、约束（成本/功耗/尺寸/离线） 2. 需求与指标 ：功能列表 + 可量化指标（TTFT<1s, tok/s>8, 内存<2GB） 3. 方案总览 ：一张分层图（应用 / 编排 / 推理 / 硬件） 4. 关键决策 ADR ：每条 = 决策 + 理由 + 备选 + 代价（最重要） 5. 数据流 ：语音/文本 → 预处理 → 推理 → 工具/RAG → 输出 6. 性能实测 ：四件套实测表（带环境） 7. 风险与降级 ：断网 / 过热 / 内存不足 各自怎么办

其中「关键决策」每条都按同一个骨架写，逼你暴露真实的权衡：

ADR 单条骨架 决策：用 RKNN int8 落地，而非 llama.cpp 理由：RK3576 有 NPU，RKNN 原生吃 NPU，能效比 CPU 高数倍 备选：llama.cpp + GGUF（跨平台好，但走 CPU，速度/功耗差） 代价：int4 在 NPU 支持有限，需退回 int8；平台被 RKNN 绑定 → 每条决策都能回答「为什么不选另一个」，文档就合格。
一句话结论：架构文档的合格线只有一条——每个技术选择都能讲清「备选是什么、为什么不要它、代价是什么」。

讲解5. 板书⑤：Demo 演示脚本（照着背，3 分钟）

演示不是「随便点两下」，而是每个演示点对应一个架构能力，串成一条有说服力的线。

3 分钟 Demo 剧本 0:00 定位一句话：「这是跑在 RK3576 上的离线语音助手，断网可用。」 0:20 演示 1 基础对话：「你好，介绍下你自己」 → 看流式输出 0:50 演示 2 function calling：「查天气 / 设 7 点闹钟」→ 看工具调用 1:20 演示 3 本地 RAG：「按我上传的手册，XX 怎么操作」→ 看检索引用 1:50 演示 4 断网降级：拔网线 → 仍能对话（本地 1.5B）→ 看鲁棒性 2:20 报指标：TTFT / tok/s / 内存 / NPU 四个数 2:40 收尾：「架构文档在这，每个决策我都能讲清理由。」
一句话结论：Demo 的目的不是「能跑」，而是让每个演示点都映射到一个架构能力——对话=推理、工具=编排、RAG=数据、断网=降级。

上午任务 4h

1

接入本地 function calling（查天气 + 设闹钟）

目标
让本地模型能调用至少 2 个本地工具，且调用请求经过本地校验后才执行。
要掌握
工具 schema 怎么写；模型输出的结构化请求怎么解析；解析失败怎么兜底。
实操步骤
写 tools_registry.py：定义 get_weather、set_alarm 两个工具（离线假数据即可）；写 agent_demo.py：把工具菜单注入 prompt，让本地模型输出 JSON 调用，本地解析并执行，再把结果回填生成自然语言回复。记录 3 个成功用例 + 1 个非法参数兜底用例。
检验标准
说「查下天气」能触发 get_weather 并返回离线天气；说「7 点叫我」能触发 set_alarm；乱说一句不会误触发工具。
2

搭一个本地轻量 RAG 知识库

目标
用本地向量库（sqlite-vec / FAISS）对一份自有文档做检索问答，全程离线。
要掌握
切块（chunk 大小 + 重叠）、向量化、top-k 检索、把检索片段拼进 prompt。
实操步骤
写 rag_local.py：① 把一份 ≥10 页的文档切块；② 向量化并写入本地向量库；③ 提问时检索 top-3 chunk；④ 拼进 prompt 让本地模型生成带来源的答案。记录索引文件大小（证明 < 50MB 级别）。
检验标准
问一个只有文档里才有答案的问题，模型能答对并引用出处；问无关问题时不硬编。
3

性能测试脚本（四件套）

目标
写一个可复用的脚本，一次跑出 TTFT / tok/s / 内存峰值 / NPU 利用率。
要掌握
怎么测首个 token 的时间；怎么稳定统计 tok/s；怎么抓进程内存峰值；怎么读 NPU 利用率。
实操步骤
写 perf_test.py：固定 prompt 跑 N 次，输出四个指标 + 运行环境（模型/量化/上下文/线程/温度）。内存用进程 RSS 采样取峰值；NPU 用平台工具（如 rknn runtime perf 或系统接口）读取。结果先存 CSV。
检验标准
脚本一条命令跑完，输出四个数；重复跑两次结果接近（说明测量稳定）。

面试话术

可直接背

「我有一个完整落地的端侧 AI agent 项目：跑在 RK3576 上，模型是 1.5B~3B int4，负责意图识别和简单对话。它支持本地 function calling——查天气、设闹钟这些工具都在本地执行，模型只吐结构化 JSON，执行权在本地代码手里；还接了本地 RAG，用轻量向量库做离线知识检索。性能上我实测了首 token 延迟、tok/s、内存峰值和 NPU 利用率四个指标，用权重体积除以内存带宽推算出理论 tok/s 是 17、实测 5~10，定位到瓶颈是内存带宽而不是算力。整个项目我写了架构设计文档，每个决策都写清了备选方案和代价，结论是每个技术选择都能讲出为什么不选另一个。」

能力标签：端到端完整项目能力——能落地、能测、能演示、能讲清架构决策。

RK3576 特别提示

  • NPU 利用率：用 RKNN runtime / 平台自带 perf 接口读取；如果 NPU 打不满 100%，多半是内存带宽喂不饱，而不是算力不够。
  • 内存要留 headroom：3B int4 权重约 2GB，加上 KV Cache、RAG 索引、运行时，留足余量，别贴着上限跑。
  • 温度与降频：长时间推理会触发热降频，tok/s 会掉——性能报告要记录温度与稳定性，别只报最好成绩。
  • 工具/RAG 全程离线：这正是端侧相对云端的最大卖点，演示时一定要真拔网线验证。
