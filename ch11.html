课堂讲义（板书）

讲解0. 这节课到底学什么

前面各章是零件：会算内存、会量化、会转换、会调优。这一章是把零件拼成一台能跑的机器。目标只有一个——端侧本地、断网、能对话，并且能拿出数字证明它跑得动。

交付物定义很硬：一段命令能启动、一个 HTTP 接口能问、本地无网能答、有一张基准性能表。做到这几条，你的简历就有了「可演示项目」。

讲解1. 板书①：项目分层架构（四层）

架构师先画图再写码。四层职责清晰，换模型/换服务方式时只动一层。

端侧 AI 助手 · 四层架构 ┌─────────────────────────────────────────┐ │ ④ 交互层 CLI 交互循环 / HTTP 接口 │ │ chat_loop.py · server.py │ ├─────────────────────────────────────────┤ │ ③ 服务层 会话管理、prompt 组装、流式输出 │ │ session.py · prompt_template.py │ ├─────────────────────────────────────────┤ │ ② 推理层 rkllm 加载 / 生成 / 采样 │ │ rkllm wrapper · callback 流式 │ ├─────────────────────────────────────────┤ │ ① 模型层 qwen2.5-3b-w4a16.rkllm + tokenizer│ └─────────────────────────────────────────┘ 设计原则：每层只依赖下一层，模型换代不动上层。 面试点：能画出这张图并说清各层职责，就是"架构"而不是"脚本"。

讲解2. 板书②：模型与工具链选型

选型结论（回顾前几章，直接给答案） 模型 Qwen2.5-1.5B / 3B Instruct（中文强、生态好） 精度 w4a16 int4（端侧甜点，内存/速度平衡） 工具链 rknn-llm（rkllm） 转 .rkllm，NPU 原生 服务 先 CLI 跑通 → 再包 HTTP（OpenAI 兼容） 为什么 1.5B 和 3B 都准备？ 3B：回答质量好，decode 约 8 t/s（带宽瓶颈） 1.5B：更轻，decode 约 15 t/s，内存 < 1GB → 3B 做质量场景，1.5B 做断网降级/极速场景 内存预算（3B int4 + 4K 上下文） 模型权重 w4a16 ≈ 2.0 GB KV Cache @4K ≈ 1.2 GB runtime + 对齐 ≈ 0.5 GB 系统 + 其它进程 ≈ 1.0 GB ───────────────────────────────── 合计 ≈ 4.7 GB （16GB 板子：安全预算内，OK）

点击展开答案（先自己填！）

KV = 上下文 × 0.28MB：2K≈0.56GB，4K≈1.2GB，8K≈2.3GB。
总占用 = 2.0(模型) + KV + 1.5(其它)：2K≈4.1GB，4K≈4.7GB，8K≈5.8GB。
16GB 都能塞下，但 8K 时 KV 已经超过模型本身一半——这就是第 4 章说的「KV 抢带宽/抢内存」，上下文不是免费拉的。

讲解3. 板书③：最小对话循环（先跑通再说）

别一上来写架构。先用官方 rkllm Python API 跑通一次「问一句、答一句」，这是所有上层的基础。

最小可跑：chat_loop.py from rkllm.api import RKLLM llm = RKLLM() llm.load_rkllm("./models/qwen2.5-3b-w4a16.rkllm", max_context=4096, num_npu_core=1) def on_token(token, status): print(token, end="", flush=True) # 流式吐字 while True: q = input("\n你> ") if q in ("exit", "quit"): break print("AI> ", end=""), llm.run(q, callback=on_token) 要点： ① load_rkllm 指定模型、上下文长度、NPU 核心 ② run 的 callback 实现流式输出（体验关键） ③ 先不管多轮、先不管包装，跑通单轮 = v0 里程碑
排错顺序：① 模型能不能 load ② 单轮能不能出字 ③ 出字是否乱码（tokenizer）④ 是否流式。按这个顺序查，别一锅乱炖。

讲解4. 板书④：包成 HTTP 服务（OpenAI 兼容）

CLI 只能自己玩。做成 HTTP 接口，才能接前端、接 App、被别人集成。做成 OpenAI 兼容格式最值钱——别人的代码改个 base_url 就能用你。

server.py（Flask 最简版，OpenAI 兼容） from flask import Flask, request, jsonify from rkllm.api import RKLLM app = Flask(__name__) llm = RKLLM() llm.load_rkllm("./models/qwen2.5-3b-w4a16.rkllm", max_context=4096) @app.post("/v1/chat/completions") def chat(): msg = request.json["messages"][-1]["content"] buf = [] llm.run(msg, callback=lambda t, s: buf.append(t)) return jsonify({ "object": "chat.completion", "choices": [{"message": {"role": "assistant", "content": "".join(buf)}}] }) if __name__ == "__main__": app.run(host="0.0.0.0", port=8000) 测试： curl http://127.0.0.1:8000/v1/chat/completions \ -H "Content-Type: application/json" \ -d '{"messages":[{"role":"user","content":"你好"}]}' 兼容 OpenAI 格式 = 生态红利：以后换更强模型， 只要接口不变，上层前端一行不用改。

讲解5. 板书⑤：基准性能记录（拿数字说话）

四项基准（demo 验收必留） ① 首 token 时延 TTFT = prompt_tokens ÷ prefill_tps 示例：512 tok ÷ 430 t/s ≈ 1.2 s ② decode 速度 = 生成 token 数 ÷ 生成耗时 示例：生成 40 tok 用 5.0s → 8.0 t/s ③ 内存 free -m 前后对比（看 RSS 增量） ④ NPU 利用率 cat /sys/kernel/debug/rknpu/load 一键采集（bench.sh 片段） free -m | awk 'NR==2{print "mem_before="$3"MB"}' START=$(date +%s.%N) # 跑一次 40-token 生成 ... END=$(date +%s.%N) echo "decode_tps=$(echo "40/($END-$START)" | bc -l)" cat /sys/kernel/debug/rknpu/load 带宽校验：decode 8 t/s × 2.0GB ÷ 35 = 45.7% 利用率 → 与第 9/10 章对上，说明记录可信。

讲解6. 板书⑥：demo v0.1 验收标准

v0.1 过关清单（全过才算完成） □ 本地无网启动 —— 拔网线还能聊 □ 首 token < 2s —— TTFT 达标 □ decode ≥ 5 t/s —— 能连续读 □ 连续对话 ≥ 10 分钟 —— 不 OOM、不崩 □ HTTP 接口可调通 —— curl 有正常返回 □ 基准表已落盘 —— 四项指标齐全 被问"项目做了什么"→ 标准答： 「我在 RK3576 上用 rknn-llm 把 Qwen2.5-3B 量化成 w4a16 并部署， 搭了四层架构的端侧 AI 助手：模型层、推理层、服务层、交互层， CLI 和 OpenAI 兼容 HTTP 都能对话，本地断网可用， 首 token 约 1.2s、decode 约 8 tok/s、内存约 2.1GB、 带宽利用率约 45%，瓶颈在内存带宽。」

能力标签：能独立交付一个可演示、可复现、有性能数字的端侧 AI 项目——最硬的面试作品。

RK3576 特别提示

  • 模型放在本地 models/（eMMC/NVMe），加载后常驻内存；首次 load 较慢，别误判为卡死。
  • 3576 内存 16GB，但 demo + 系统 + KV + 其它服务要一起算；3B int4 建议上下文 ≤4K，8K 会让 KV 涨到 2.3GB。
  • NPU 单核，服务端并发（batch）能把带宽利用率从 ~45% 拉到 ~80%，是提升吞吐的正道。
  • demo 用 1.5B 做断网降级/极速模式、3B 做质量模式——一套代码两个档位，面试时是加分项。
  • HTTP 服务记得绑 0.0.0.0 才能被外部访问；生产要加超时与限流，避免长 prompt 打满内存。
