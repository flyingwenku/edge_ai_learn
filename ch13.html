课堂讲义（板书）

讲解0. 这节课到底学什么

前面几章都在"算账"。这一章开始动手：把一套完整的端侧部署链路走通一遍。链路四步——装系统 → 配工具链 → 转模型 → 跑推理。四步都通，"手里有真板子"就从概念变成了可复现的工程能力。

讲解1. 板书①：烧录系统（镜像 + 工具）

第一步：给 RK3576 装系统（两条路线） 路线 A：厂商成品镜像（推荐，最省事） 1. 下载 .img 镜像（Debian 12 / Ubuntu 22.04） · 来源：板子厂商（Firefly / Toybrick / 香橙派 / 瑞芯微官方） · 选对应板型 + 需要 NPU 驱动齐全的镜像 2. 工具：Windows 用 RKDevTool；Linux 用 upgrade_tool 3. 板子进入 Loader / MaskROM 模式（按住 recovery 键或短接，USB 连接电脑） 4. RKDevTool → "升级固件" → 选 .img → 执行 → 等待完成 路线 B：SD 卡烧录（部分板支持） 用 balenaEtcher 把 .img 写到 TF 卡 → 插卡 → 上电启动 烧完先做三件验证 uname -a # 看内核与架构 (aarch64) cat /proc/device-tree/model # 确认是 RK3576 cat /sys/kernel/debug/rknpu/version # 确认 NPU 驱动存在 登录方式 串口 / HDMI 接屏幕；或网线 SSH（默认用户常见：linaro / firefly / rock / root） 默认密码厂商各异（常见：firefly / linaro / rockchip / 空）
先别急着跑模型：镜像一定要选"带 NPU 驱动（rknpu）"的，否则后面 RKNN 一律跑不起来。/sys/kernel/debug/rknpu/version 能读出东西，才算烧对。

讲解2. 板书②：安装 RKNN 工具链（上位机 + 板端，别装错机器）

RKNN 工具链分两半，装错机器 = 白折腾 【上位机 x86 Ubuntu 20.04 / 22.04】—— 负责"转换 + 量化" pip install rknn-toolkit2 # Python 3.8 / 3.10 python3 -c "from rknn.api import RKNN; print('ok')" # 验证 → 作用：把 ONNX 模型转成 .rknn（这一步在电脑上做） 【板端 RK3576】—— 负责"推理" 运行库：librknnrt.so（与板端 NPU 驱动对应） Python 轻量包：rknn-toolkit-lite2 # CNN 推理（.rknn） LLM 运行时：librkllmrt.so + rkllm # LLM 推理（.rkllm，两套不是一回事） git clone https://github.com/airockchip/rknn_model_zoo → 作用：加载 .rknn 跑推理 版本必须对齐！ rknn-toolkit2 版本 ↔ librknnrt.so 版本 ↔ NPU 驱动版本 不一致 → 报 "version mismatch" 或直接跑不动。 查板端运行库版本：strings librknnrt.so | grep -i version 查 NPU 驱动：cat /sys/kernel/debug/rknpu/version
口诀：转换在上位机，推理由板端；两边版本必须能用同一套号。记不住就去 rknn_model_zoo 的 README 找"对应关系表"。

讲解3. 板书③：转换一个 1.5B 模型到 RKLLM（.rkllm）

常见误区：以为 LLM 也能用 toolkit2 从 ONNX 转 .rknn、再用 lite2 加载。 LLM 必须走 rknn-llm（rkllm），产物是 .rkllm；rknn-toolkit2 只处理 ONNX 类模型（CNN/ViT）， 而 rkllm 只接受 HF 模型目录或 GGUF，不接受 ONNX。
以 Qwen2.5-0.5B/1.5B 为例（rknn-llm 链路） ① 准备：拿 HF 模型目录（不是 onnx） git clone https://github.com/airockchip/rknn-llm # 从 ModelScope 克隆 Qwen/Qwen2.5-0.5B-Instruct（HF 源常不可达） ② 生成量化校准集（CPU 跑，别用随机数据） cd examples/rkllm_api_demo/export python -u generate_data_quant.py -m -o data_quant.json --max-new-tokens 64 # 官方 21 条够跑通；要验 W4A16 质量问题建议 50 条（grq 耗时对样本数超线性） ③ 转换（一条命令出 .rkllm） python -u export_rkllm.py --model-dir --dataset data_quant.json \ --output qwen25-0.5b_w8a8.rkllm --device cpu --dtype float32 \ --target-platform RK3576 --num-npu-core 2 \ --quantized-dtype W8A8 --quantized-algorithm normal \ --optimization-level 0 --max-context 4096 # W4A16 必须配 --quantized-algorithm grq；用 normal 会严重语义退化 ④ 产物与实测（0.5B） W8A8 + normal → 811 MB，峰值 0.73 GB，decode 20.07 tok/s W4A16 + grq → 527 MB，峰值 0.46 GB，decode 36.87 tok/s （W4A16 快 1.84×，但 0.5B 上语义退化，默认仍选 W8A8） 坑提示 · 校准集规模与耗时超线性：21 条≈30min，50 条≈1.5~1.8h，125 条≈4~5h · grq 导出峰值内存接近 7 GB：WSL 给足物理内存（7GB+8G swap），别只加 swap · 日志看两处：输出文件句柄 /proc/<pid>/fd 出现 rkllm = 开始落盘；/proc/<pid>/stat 状态 R/D/T
高效的偷懒正确姿势：先跑通官方示例，再换自己的模型。不要一上来就自己写导出脚本——LLM 的 RoPE/KV Cache 布局是深坑，zoo 已经踩过了。

讲解4. 板书④：在板子上跑通推理 + 记录四项指标

把模型推到板子 + 登录（LLM 用 .rkllm，不是 .rknn） # 传输（二选一） scp qwen25-0.5b_w8a8.rkllm radxa@<IP>:/home/radxa/ # 或 python code_tools/ip_bro/tools/sshx.py --put <local> <remote> 板端跑 rkllm demo export LD_LIBRARY_PATH=/home/radxa/rkllm_api_demo/lib ./llm_demo <model.rkllm> 4096 "你好，介绍一下你自己" # 起服务：flask_server.py --rkllm_model_path <model.rkllm> --target_platform rk3576 # 实测入口：/rkllm_chat、/rkllm_clear、/rkllm_abort 要记录的 4 个指标 ① 首 token 延迟 TTFT：从发送 prompt 到吐出第一个 token（受 prefill 影响） ② 生成速度 tok/s：后续 token 的稳态速度（受 decode 带宽影响） ③ 内存占用：free -m （看 used / available） ④ NPU 利用率：cat /sys/kernel/debug/rknpu/load 实测输出形如：NPU load: Core0: 78%, Core1: 0% 注意：Core1 为 0% 往往是你没开双核，不是它不存在 辅助命令 free -m # 内存 cat /proc/meminfo | head # 内存细节 cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq # CPU 频率 cat /sys/kernel/debug/rknpu/load # NPU 负载（两核分别显示）

记录模板（每次实验一行，先自己填一栏再展开答案）：

inference_metrics.csv model, quant, prompt_len, ttft_ms, tok_per_s, mem_used_mb, npu_pct, note qwen2.5-1.5b, w8a8, 32, ___, ___, ___, ___, 短 prompt qwen2.5-1.5b, w8a8, 512, ___, ___, ___, ___, 长 prompt（看 TTFT 上升）
点击展开答案（参考量级，实测为准）
本板实测（0.5B）与 1.5B 推算： · 0.5B W8A8：初始化 1.39s；prefill 324.5 tok/s（64 tok → 0.2s） decode 20.07 tok/s；峰值内存 0.73 GB · 0.5B W4A16+grq：decode 36.87 tok/s；峰值 0.46 GB（但语义退化） · 1.5B W8A8（推算）：权重 ~1.6GB，decode 约 6~9 tok/s（带宽受限） · NPU：生成阶段 Core0 常见 60~90%；Core1 为 0% = 没开双核 关键：数字不重要，"趋势"才重要—— prompt 越长 → TTFT 越大；上下文越长 → tok/s 越低。

讲解5. 板书⑤：RK3576 性能画像与三条铁律

RK3576 性能画像（必须背） NPU 6 TOPS / 2 核 ← 算力够（本板可行档 0.5B~1.5B） 内存带宽 19 / 12~16 / 7~11 GB/s ← 真正的瓶颈（理论/NPU 独占/产品，decode 打产品档） CPU 4×A72 + 4×A53 ← CPU 弱，别指望 CPU 兜底 内存 SoC 上限 16GB / 本板实测 3.8 GiB 三条铁律 ① 优先纯 NPU 推理：一旦有算子回落到 CPU， 速度会被 CPU 拖垮（3576 的 CPU 很弱）。 ② 带宽是命门：能减小的权重 / KV 一定要减（量化 + GQA）。 ③ 首 token 慢是正常的：prefill 要算完整个 prompt， 长 prompt 的 TTFT 会明显上升。 自测基准（参考，实测为准） Qwen2.5-0.5B w8a8：prefill 324.5 tok/s、decode 20.07 tok/s、峰值 0.73GB Qwen2.5-1.5B w8a8（推算）：decode 约 6~9 tok/s 如果实测远低于此 → 查两件事： (a) 有没有算子回落到 CPU？（看日志 fallback / cpu 提示） (b) 模型是不是没跑在 NPU 上？（NPU load 一直 0% = 没上 NPU）
排障第一反应：速度不对，先看 rknpu/load。NPU 利用率为 0 或很低，说明大量算子在 CPU 上跑——这才是端侧最常见的性能坑。
实测补充 · 板端救援四件事（教程常漏，但每天都会用到）：
  • 看门狗：硬件狗 20s 超时且 nowayout=1，printf V > /dev/watchdog 关不掉，只能持续喂；程序里内置喂狗线程（每 5s 一次），否则整机每 20s 重启。
  • 日志刷屏：i2c 类错误会毫秒级刷，先 echo "2 4 1 7" > /proc/sys/kernel/printk 再调试，否则真错误看不见。
  • 持久化：/tmp 是 tmpfs（重启即清），/opt 是 ubifs rw；修模型软链、配置要落在 /opt。
  • 连不上：ping 通但 22/8080 不通，先比 MAC（IP 冲突，ARP 指向别人），比扫端口有效；串口（115200 8N1）是最后兜底。

本节要点回顾

要点回顾
  • RK3576 端侧部署是一条四步链路：烧系统 → 配工具链 → 转模型 → 跑推理，四步打通才算走完。
  • 系统镜像必须带 NPU 驱动；烧完先用 /sys/kernel/debug/rknpu/version 验证驱动存在。
  • 工具链分两套：CNN/ViT 走上位机 rknn-toolkit2 → .rknn，板端 librknnrt.so + rknn-toolkit-lite2；LLM 走 rknn-llm → .rkllm，板端 librkllmrt.so + rkllm。两边版本都要对齐。
  • LLM 转换用 rknn-llm：HF 目录 → 校准集 → export_rkllm.py → .rkllm（0.5B W8A8 811MB）。rkllm 不收 ONNX；W4A16 必须配 grq。
  • 板端跑通后记录四项指标：TTFT、decode tok/s、内存占用、NPU 利用率，重点看趋势而非单点数字。
  • 3576 的瓶颈是内存带宽（峰值 19 / NPU 独占 12~16 / 产品 7~11 GB/s）与弱 CPU，所以优先纯 NPU 推理，一旦算子回落 CPU 速度会被拖垮。
  • 性能不对时先看 rknpu/load：利用率长期为 0 说明大量算子在 CPU 上跑，这是端侧最常见的性能坑。

RK3576 特别提示

  • 镜像务必选带 NPU 驱动的固件；烧完先验证 /sys/kernel/debug/rknpu/version。
  • 带宽三档：峰值 19 / NPU 独占 12~16 / 产品 7~11 GB/s，CPU 弱——一旦算子回落 CPU，速度会被拖垮，优先纯 NPU。
  • 日志里搜 fallback / cpu；性能差先看 rknpu/load，NPU 利用率为 0 说明没好利用 NPU。
  • 优先用 rknn_model_zoo 已支持的模型（Qwen2.5 等），别一上来自己写 LLM 导出脚本。
  • 长 prompt 的 TTFT 上升属正常（prefill），别误判为"模型有问题"。
