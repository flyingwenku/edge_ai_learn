课堂讲义（板书）

讲解0. 这节课到底学什么

第 1~2 章你搞定了「模型多大、怎么量化」。但一个 .gguf 或 .rknn 文件，怎么变成屏幕上滚动的字？中间是推理框架在干活。这一章就把「框架是谁」「模型怎么转过去（ONNX 中间层）」「流程怎么走」「时间花在哪」讲透——这是面试官问「你怎么落地」时的第一道题。

一句话记住：框架选错，模型再好也跑不动；流程看不懂，就定位不了卡顿。

讲解1. 板书①：六个框架，先按「谁写的、给谁用」归位

别背参数，先分阵营。所有推理框架只分两类：通用跨平台 和 芯片官方。

框架阵营 / 出身吃谁的算力量化端侧适配典型产物
llama.cpp社区，C++ 轻量引擎CPU（+部分 GPU）GGUF（Q4_K_M 等）跨平台验证之王.gguf
MNN阿里，轻量引擎手机 CPU/GPU自有 int8/int4移动端部署强.mnn
TFLiteGoogle，Android 生态Android CPU/NPU delegateint8 为主安卓离线模型.tflite
ONNX Runtime微软，通用运行时多后端 EP（CPU/GPU/NPU）依赖 EP通用中间格式最强.onnx
RKNN瑞芯微官方RK NPU 原生int8 / per-channel PTQ3576 官方支持.rknn
QNN高通官方骁龙 Hexagon NPUint8/int16只吃高通芯片.cpp/.bin
判断口诀（背下来）： 芯片官方工具（RKNN / QNN） = 能吃满自家 NPU，性能最好 但 只认自家芯片 通用框架（llama.cpp / ONNX / MNN / TFLite） = 换平台方便 但 对专用 NPU 只吃个皮毛 一句话：落地认官方，验证认通用。

讲解2. 板书②：为什么 RK3576 一定用 RKNN

RKNN 不是「一个软件」，而是瑞芯微的一整套工具链。搞清三件套，你就知道数据是怎么流的。

RKNN 三件套： 1) rknn-toolkit2 → 在 PC 上把 onnx 转成 .rknn（内含量化） 2) librknnrt → 板端 运行时库，真正调 NPU 3) rknn_server → 板端服务（PC 联调时用） 支持芯片：RK3576 / RK3588 / RK3566 / RK3562 …（3576 在列 ✅） 量化口径：int8 为主，per-channel PTQ，必须给校准集 选型边界： 芯片是 RK 系 → RKNN（唯一正解） 芯片不是 RK → RKNN 用不了，回头找通用框架或厂商工具
结论句：「只要目标板是 RK3576，模型最终一定编成 .rknn 走 NPU，别无他路。」

讲解3. 板书③：ONNX 基础（转换链路的中间层）

上一节那句「在 PC 上把 onnx 转成 .rknn」，这个 onnx 到底是什么？它是端侧落地链路上绕不开的中间层。

为什么需要 ONNX？ 训练框架各家不同：PyTorch / TensorFlow / Paddle…… 部署引擎也各家不同：RKNN / QNN / TensorRT / OpenVINO…… 如果两两直连，要写 N×M 个转换器 → 组合爆炸。 ONNX 站出来当「通用中间格式」： PyTorch ──导出──▶ ONNX ──转换──▶ RKNN(.rknn) / QNN / … 一次导出、多方消费 → 把 N×M 收敛成 N+M。 端侧链路（本课主线）： PyTorch 权重 ──export──▶ ONNX(.onnx) ──rknn-toolkit2──▶ .rknn ──▶ RK NPU
ONNX 的两个核心概念： ① 图（Graph） ONNX 把模型存成一张「计算图」： node（算子）+ tensor（张量）+ initializer（权重常量）。 · 算子 = Add / MatMul / Softmax / Conv / Reshape … · 张量 = 数据流，带名字和 shape（常有动态维，如 batch/seq 用 '?'） ② opset（算子集版本） opset 是「该用哪个版本的算子定义」的版本号。 · opset 太低 → 老算子表达不了新模型（如 RoPE、SwiGLU） · opset 太高 → 目标工具链还不认识 → 转换报错 · 经验：导出时选目标工具链支持范围内的 opset（RKNN 常停在中等版本） 一句话：opset 是 ONNX 与下游工具链之间的"接口版本"。
为什么转换报错，多半是 ONNX 算子不兼容？ PyTorch 里一个简单操作，导出后可能是自定义 / 融合 / 高版本算子： · 用了 RKNN/TFLite 不支持的算子 → Unsupported operator · 动态 shape 推断不出来 → shape 报错 · opset 与目标工具链不匹配 → 版本报错 排查顺序（背下来）： ① 看报错里点名的算子名 → 是不是在目标工具链支持列表里 ② 用 netron 打开 onnx，肉眼找可疑算子（自定义/高版本） ③ 回 PyTorch 侧改写：换等价算子、去掉不支持的 op、固定 shape、调 opset 结论：端侧模型转换的坑，八成都出在 ONNX 这一层。
用 netron 看模型（实操工具） netron = 开源的模型可视化工具，双击 .onnx / .rknn 就能看图。 能看：算子名字、连接关系、每层 shape、权重张量大小。 用途：确认导出对不对、找不兼容算子、核对输入输出名字/shape。 （它是 PC 上的工具，不用装到板子上。）
面试点：「PyTorch 到 RKNN 中间要过 ONNX 这一层——它是跨框架的通用交换格式；转换报错大多不是模型写错，而是 ONNX 算子/opset 与目标工具链不兼容，我会用 netron 定位到具体算子再回 PyTorch 改写。」

讲解4. 板书④：推理全流程拆解

从文本到文本，一共六步。每一章后面都会拆其中一段，这里先建全局地图。

推理流程（从文本到文本）： tokenize 文本 → token id （BPE / SentencePiece 分词器） ↓ embedding id → 向量 [hidden] （查表，一次搞定） ↓ N × Transformer 层: LayerNorm → Attention → 残差 LayerNorm → FFN → 残差 ↓ logits 最后位置的向量 → [vocab] 维分数 ↓ sampling greedy/top-k/top-p/temperature → 选出 1 个 id ↓ detokenize id → 文本 （拼回可读字符串） 架构师关注点：tokenize/detokenize 是 CPU 小开销， 真正吃时间的是 N × Transformer 层 和 sampling。

讲解5. 板书⑤：prefill 与 decode —— 两阶段性质完全不同

很多人以为「生成」是一件事，其实是两个物理过程。这是本章最重要的一张板书。

【Prefill 预填充】 输入：整段 prompt（比如 512 个 token），一次性并行处理 算子：矩阵 × 矩阵（matmul）→ 算力密集（compute-bound） 目的：把这 512 个 token 的 K/V 全部算好，存进 KV Cache 指标：tokens/s，衡量「吃 prompt 快不快」 【Decode 解码】 输入：每次只喂 1 个 新 token 算子：矩阵 × 向量（matvec）→ 带宽密集（memory-bound） 目的：算下一个 token，把新 K/V 追加进 Cache 指标：tokens/s，衡量「吐字快不快」 同一个模型，prefill 吞吐常是 decode 的 5~10 倍。 原因：matmul 每读一次权重能算一大片；matvec 每步都要把 2GB 权重全读一遍。
面试点：「首字延迟看 prefill，出字速度看 decode」——这句能立刻区分内行和外行。

讲解6. 板书⑥：用 llama.cpp verbose 看每步耗时

光讲理论不行，得会看数据。llama.cpp 加 -v（verbose）就会打印分段耗时。

命令： llama-cli -m qwen2.5-3b-Q4_K_M.gguf -p "你好" -n 128 -v 看这几行： load time = 加载模型耗时（磁盘 IO + 解量化） prompt eval time = prefill 耗时 / token 数 eval time = decode 耗时 / token 数 total time = 端到端总耗时 手算示范： prompt eval 512 tok / 12.0 s → 512 / 12.0 = 42.7 tok/s（prefill） eval 128 tok / 16.0 s → 128 / 16.0 = 8.0 tok/s（decode） load 2.1 s 判读： decode 8 tok/s 就是用户看到的出字速度；这才是优化重点。 prefill 慢 → 首字延迟高（长 prompt 场景要专门优化）。

讲解7. 板书⑦：选型决策（背下来）

场景 → 框架 RK3576 生产落地 → RKNN（.rknn，吃 NPU，性能最好） 跨平台 / 快速验证 → llama.cpp + GGUF Q4_K_M（CPU 就能跑） Android 原生 App → MNN / TFLite 高通平台（如手机） → QNN 被问「RK3576 + 3B 用什么框架」→ 标准答： 「生产用 RKNN，官方 NPU 支持最好、能吃到 6 TOPS； 开发和验证阶段用 llama.cpp 跑 GGUF Q4_K_M，方便跨平台对比。 两者产物不通用，最终要转 .rknn。」

可直接背

「推理框架分两类：芯片官方工具和通用框架。RK3576 的 NPU 是瑞芯微自己的，所以生产落地我一定用 RKNN——它是官方工具链，onnx 经 rknn-toolkit2 转成 .rknn，板端 librknnrt 直接吃 NPU，能拿到 6 TOPS 的算力。开发和跨平台验证阶段我会用 llama.cpp 跑 GGUF Q4_K_M，因为它 CPU 就能跑、方便对比，但它吃不满 NPU，最终产物还要转回 RKNN。中间这一层是 ONNX：PyTorch 到 RKNN 必须过 ONNX，因为它是跨框架的通用交换格式，链路是 PyTorch→ONNX→.rknn；转换报错十有八九不是模型写错，而是 ONNX 算子或 opset 跟目标工具链不兼容，我会用 netron 打开计算图定位到具体算子，再回 PyTorch 侧改写。推理流程上，prefill 是把整段 prompt 并行算、矩阵乘矩阵、偏算力；decode 是逐 token 生成、矩阵乘向量、受内存带宽限制，所以首字延迟看 prefill、出字速度看 decode。」

能力标签：能说清「用什么框架、为什么用、模型怎么转过去、流程卡在哪」——框架选型、模型转换与性能拆解能力。

RK3576 特别提示

  • 3576 的 NPU 算力约 6 TOPS（int8），只有走 RKNN 才吃得到；用 llama.cpp 只跑 CPU，吃不到 NPU。
  • 模型落地链路是 PyTorch → ONNX → .rknn：ONNX 这层的算子/opset 兼容性直接决定转换成败。
  • RKNN 转换必须给校准集，第 9 章会用真实数据做校准。
  • 端侧首字延迟主要卡在 prefill，长 prompt 场景要专门优化（如分块、批处理）。
  • decode 阶段是带宽瓶颈（第 5 章展开），3576 的 35 GB/s 是硬约束。
