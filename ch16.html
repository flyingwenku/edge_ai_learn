课堂讲义（板书）

讲解0. 这节课到底学什么

前面各章是零件：会算内存、会量化、会转换、会调优。这一章是把零件拼成一台能跑的机器。这版 demo 有两个目标——端侧本地、断网、既能「看」（摄像头检测）又能「说」（本地对话），而且能拿出数字证明两个模型在同一块 16GB 板子上共存还跑得动。

交付物定义很硬：一段命令能启动、一个 HTTP 服务既能问（对话）又能看（检测）、本地无网能答、有一张双任务基准表。做到这几条，才算把前 15 章的知识收成了一个可运行的多模态端侧工程。

讲解2. 板书②：双任务升级——CV 检测 + 本地 LLM 共存

只做对话的 demo 价值有限，无非给模型套了个壳。升级为「感知 + 交互」双任务，才真正触到端侧的核心矛盾：两个模型抢同一块 NPU 和同一片内存，怎么排兵布阵。分工先记牢：CV 管「看」，LLM 管「说」。

双任务数据流（不是流水线，是共享资源的两个任务） 摄像头帧(15~30fps) ──► 预处理 resize / 归一化 │ ▼ ① 感知：CV 检测模型（YOLOv8n，int8 .rknn，跑 NPU） 每帧 → 检测框 / 类别 / 置信度 → JSON │ （去抖：连续 N 帧稳定才升级为"事件"） ▼ ② 事件聚合：把逐帧检测压成"发生了什么" 例：连续 10 帧出现 person → 事件 {person, 持续 0.7s} │ ▼ ③ 交互：本地 LLM（Qwen2.5-1.5B/3B，w4a16 .rkllm，跑 NPU） 把事件/摘要拼进 prompt → 生成自然语言解释 / 回答 │ ▼ ④ 输出：屏幕 / TTS / HTTP 返回 分工一句话：CV 管"看"（瞬时、结构化、低延迟）， LLM 管"说"（语义、交互、可解释）。 两者共享 NPU + 内存，谁也离不开谁，但要抢资源。

第一个要算的账：内存预算。很多人一听「双模型」就慌，其实检测模型小得可怜。看数：

双任务内存预算（3B LLM + YOLOv8n，4K 上下文） LLM 权重 w4a16 ≈ 2.000 GB LLM KV Cache @4K ≈ 1.200 GB LLM runtime + 对齐 ≈ 0.500 GB CV 模型 YOLOv8n int8 ≈ 0.005 GB ← 才 5 MB！ CV runtime / 激活 / 帧缓冲 ≈ 0.045 GB 系统 + 其它进程 ≈ 1.000 GB ───────────────────────────────────────── 合计 ≈ 4.75 GB（16GB 板：宽裕） 关键结论：CV 检测模型只有几 MB， 真正吃内存的仍是 LLM 的权重 + KV。 所以"双任务内存不够"的锅，永远先算 LLM 那笔账。

第二个要算的账：NPU 时间片。RK3576 只有一块 NPU，CV 和 LLM 都得排队用它。先把各自的占用算清楚：

NPU 时间片与并发 RK3576 NPU：int8 6 TOPS，一块共享的加速资源 CV 检测(YOLOv8n 640, int8)：单帧 ≈ 12 ms LLM(Qwen2.5-3B) decode：NPU 独占 6~8 t/s → 单 token ≈ 125~167 ms（带宽受限） CV 吃掉多少 NPU 时间片？ 15 fps：15 × 12 ms = 180 ms/s → 18% 30 fps：30 × 12 ms = 360 ms/s → 36% → 检测很轻，NPU 算力完全够。CV 从来不是算力问题。 冲突点：LLM 的一次长 prefill（512 token ≈ 1.2s）会把 NPU 占满， 这 1.2s 内 CV 帧只能排队 → 检测掉帧、报警延迟。 共存策略（按优先级）： ① 事件驱动：无目标时 CV 降到 5fps 空跑，检测到目标才叫 LLM ② 时间片：给 CV 保底帧率（如 10fps），LLM prefill 分块让路 ③ 分核/多实例：NPU 支持多核时 CV 与 LLM 各占核 ④ 降上下文：prefill 越短，占坑越少

第三个要算的账：谁才是瓶颈。三项资源（算力 / 时间片 / 带宽）一起看，别拍脑袋：

双任务瓶颈判定 NPU 算力 ：CV 18~36% + LLM 少量 → 有余量，不是瓶颈 NPU 时间片：并发时 CV 被 LLM 长 prefill 饿到 → 次要瓶颈 内存带宽 ：LLM decode 每 token 读 2GB → NPU 独占 12~16 GB/s → 6~8 t/s 产品场景被摄/屏抢到 7~11 GB/s → 3.5~5.5 t/s → 主瓶颈 内存容量 ：双任务 ≈ 4.75GB / 16GB → 不是瓶颈 一句话：双任务 demo 的瓶颈，主因仍是 LLM 的内存带宽； CV 只是"抢时间片"的次要矛盾。优化先压 LLM 带宽（量化 / 前缀缓存）， 再去谈给 CV 让路。
带宽利用率 = decode_tps × 权重_GB ÷ 有效带宽上限（NPU 独占 12~16 / 产品 7~11 GB/s）

NPU 时间片 = 帧率 × 单帧毫秒 ÷ 1000：15fps → 18%，30fps → 36%。
内存合计 = LLM 权重 + KV + runtime(0.5) + CV(0.05) + 系统(1.0)：
· 3B / 2K：2.0 + 0.56 + 0.5 + 0.05 + 1.0 ≈ 4.11GB → 流畅；
· 3B / 4K：2.0 + 1.2 + 0.5 + 0.05 + 1.0 ≈ 4.75GB → 可行，但 30fps 时并发会互相拖累；
· 1.5B / 4K：1.0 + 0.6 + 0.5 + 0.05 + 1.0 ≈ 3.15GB → 内存宽松，代价是回答质量下降。
注意：三行里 NPU 时间片都不高（≤36%），说明算力不是瓶颈，真正的坎是 LLM 的带宽和并发时的排队。

讲解3. 板书③：模型与工具链选型

选型结论（回顾前面各章，直接给答案） 模型 Qwen2.5-1.5B / 3B Instruct（中文强、生态好） 精度 w4a16 int4（端侧甜点，内存/速度平衡） 工具链 rknn-llm（rkllm） 转 .rkllm，NPU 原生 检测模型 YOLOv8n（int8） → .rknn，NPU 感知 服务 先 CLI 跑通 → 再包 HTTP（OpenAI 兼容 + /detect） 为什么 1.5B 和 3B 都准备？ 3B：回答质量好，decode 约 6~8 t/s（NPU 独占；产品 3.5~5.5，带宽瓶颈） 1.5B：更轻，decode 约 7~11 t/s（产品）／12~16（NPU 独占），内存 ~1GB → 3B 做质量场景，1.5B 做断网降级/极速场景 为什么检测走 RKNN 而不是 rkllm？ rkllm 是 LLM 专用工具链；检测是 CNN， 用 RKNN Toolkit 把 YOLOv8n 转成 .rknn，直吃 NPU。 同一个 NPU，两套工具链产物——这正是"共享硬件"的落地。 内存预算（3B int4 + 4K 上下文） 模型权重 w4a16 ≈ 2.0 GB KV Cache @4K ≈ 1.2 GB runtime + 对齐 ≈ 0.5 GB 系统 + 其它进程 ≈ 1.0 GB ───────────────────────────────── 合计 ≈ 4.7 GB （16GB 板子：安全预算内，OK）

讲解4. 板书④：最小对话循环（先跑通再说）

别一上来写架构。先用官方 rkllm Python API 跑通一次「问一句、答一句」，这是所有上层的基础。

最小可跑：chat_loop.py from rkllm.api import RKLLM llm = RKLLM() llm.load_rkllm("./models/qwen2.5-3b-w4a16.rkllm", max_context=4096, num_npu_core=1) def on_token(token, status): print(token, end="", flush=True) # 流式吐字 while True: q = input("\n你> ") if q in ("exit", "quit"): break print("AI> ", end=""), llm.run(q, callback=on_token) 要点： ① load_rkllm 指定模型、上下文长度、NPU 核心 ② run 的 callback 实现流式输出（体验关键） ③ 先不管多轮、先不管包装，跑通单轮 = v0 里程碑
排错顺序：① 模型能不能 load ② 单轮能不能出字 ③ 出字是否乱码（tokenizer）④ 是否流式。按这个顺序查，别一锅乱炖。

讲解5. 板书⑤：包成 HTTP 服务（OpenAI 兼容 + 检测接口）

CLI 只能自己玩。做成 HTTP 接口，才能接前端、接 App、被别人集成。做成 OpenAI 兼容格式最值钱——别人的代码改个 base_url 就能用你。双任务版本再加一个感知接口。

server.py（Flask 最简版，OpenAI 兼容） from flask import Flask, request, jsonify from rkllm.api import RKLLM app = Flask(__name__) llm = RKLLM() llm.load_rkllm("./models/qwen2.5-3b-w4a16.rkllm", max_context=4096) @app.post("/v1/chat/completions") def chat(): msg = request.json["messages"][-1]["content"] buf = [] llm.run(msg, callback=lambda t, s: buf.append(t)) return jsonify({ "object": "chat.completion", "choices": [{"message": {"role": "assistant", "content": "".join(buf)}}] }) @app.post("/detect") # 双任务新增：感知接口 def detect(): frame = cv.capture_once() boxes = detector.run(frame) # 返回结构化检测结果 return jsonify(boxes) # [{"cls","conf","box"}, ...] if __name__ == "__main__": app.run(host="0.0.0.0", port=8000) 测试： curl http://127.0.0.1:8000/v1/chat/completions \ -H "Content-Type: application/json" \ -d '{"messages":[{"role":"user","content":"你好"}]}' 对话走 /v1/chat/completions，感知走 /detect， 一个服务两个能力——这就是"多模态端侧"的最小形态。

讲解6. 板书⑥：基准性能记录（拿数字说话）

五项基准（双任务 demo 验收必留） ① 首 token 时延 TTFT = prompt_tokens ÷ prefill_tps 示例：512 tok ÷ 430 t/s ≈ 1.2 s ② decode 速度 = 生成 token 数 ÷ 生成耗时 示例：生成 40 tok 用 6.7s → 6.0 t/s ③ 内存 free -m 前后对比（看 RSS 增量） ④ NPU 利用率 cat /sys/kernel/debug/rknpu/load ⑤ 双任务并发（本章升级项） CV 实测 fps + LLM decode 的互相掉幅 → 并发掉幅越小，说明时间片策略越好 一键采集（bench_dual.sh 片段） free -m | awk 'NR==2{print "mem_before="$3"MB"}' # 启动 CV 检测（15fps）... # 同时跑一次 40-token LLM 生成 ... START=$(date +%s.%N) # ... 生成 40 token ... END=$(date +%s.%N) echo "decode_tps=$(echo "40/($END-$START)" | bc -l)" echo "cv_fps=$(cat /tmp/cv_fps.txt)" cat /sys/kernel/debug/rknpu/load 带宽校验：decode 6 t/s × 2.0GB ÷ 16 = 75% 利用率（对 NPU 独占上沿） → 与前面的带宽口径对上，说明记录可信。

本节要点回顾

  • 端侧 AI 助手按四层拆：模型层 / 推理层 / 服务层 / 交互层，层间单向依赖，换模型或换接口只动对应一层。
  • 「感知 + 交互」双任务是本章核心形态：CV 检测负责「看」，本地 LLM 负责「说」，两者共享同一块 NPU 与同一片内存，必须抢资源。
  • 双任务内存合计约 4.75GB（3B int4 + 4K 上下文）：LLM 权重 2.0GB、KV 1.2GB、CV 仅 0.05GB，吃内存的始终是 LLM。
  • NPU 时间片：CV 检测 15fps 约占 18%、30fps 约占 36%，检测本身很轻；冲突点在 LLM 的长 prefill 会饿到 CV。
  • 双任务瓶颈判定：主瓶颈是 LLM 的内存带宽（每 token 读 2GB 权重），次要才是 NPU 时间片，算力与容量都不是瓶颈。
  • 共存策略按优先级：事件驱动降帧 → 给 CV 保底帧率并让 LLM 分块 prefill → NPU 多核分核 → 缩上下文。
  • 最小对话循环三步：load_rkllm 加载 → run 推理 → callback 流式输出，跑通单轮即 v0 里程碑。
  • HTTP 服务用 OpenAI 兼容的 /v1/chat/completions 加 /detect：一个进程两个能力，即多模态端侧的最小形态。
  • 验收看数字：TTFT < 2s、decode ≥ 4 t/s、CV 单帧 ≈12ms、并发内存峰值 < 6GB，且带宽利用率与公式一致。

RK3576 特别提示

  • 模型放在本地 models/（eMMC/NVMe），加载后常驻内存；首次 load 较慢，别误判为卡死。
  • 3576 内存 16GB，但 demo + 系统 + KV + 检测缓冲 + 其它服务要一起算；3B int4 建议上下文 ≤4K，8K 会让 KV 涨到 2.3GB。
  • 检测模型务必走 RKNN Toolkit（int8 .rknn），不要用 rkllm——rkllm 只吃 LLM。
  • NPU 是共享资源，CV 与 LLM 会抢时间片：给 CV 设保底帧率，LLM prefill 尽量分块；NPU 多核时优先给两者分核。
  • NPU 单核场景下，服务端并发（batch）能把带宽利用率从 ~75% 拉到 ~98%，是提升吞吐的正道。
  • demo 用 1.5B 做断网降级/极速模式、3B 做质量模式——一套代码两个档位，能覆盖更多场景。
  • HTTP 服务记得绑 0.0.0.0 才能被外部访问；生产要加超时与限流，避免长 prompt 打满内存。
  • 带宽口径统一记住：RK3576 LPDDR5-4800 峰值 ≈19GB/s，NPU 独占 12~16GB/s，产品场景 7~11GB/s。
